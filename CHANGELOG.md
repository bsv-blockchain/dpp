# Changelog

This file records what a consumer of the `@bsv/dpp-*` packages, the contracts and the fixtures needs: the changes in the unpublished candidate and the releases already published. Every package is an experimental beta prerelease whose API may change significantly. The standard is pre-1.0, so breaking changes are expected and recorded here without apology until version 1.0 is declared, as `GOVERNANCE.md` states. [Migration](docs/migration.md) gives the steps for each change that needs one.

## Unpublished: dpp-release-2026-11

`dpp-release-2026-11` is the current candidate: `@bsv/dpp-protocol` and `@bsv/dpp-profiles` `0.3.0-beta.10`, `@bsv/dpp-overlay` `0.4.0-beta.13`, `@bsv/dpp-credentials` `0.2.0-beta.6` and `@bsv/create-dpp-app` `0.1.0-beta.2`. Each line below is a change since the last publication, `dpp-release-2026-10-10` on 16 October 2026. A step number is a step of [test the November source candidate](docs/migration.md#test-the-november-source-candidate).

What this candidate adds, in short:

- **Bound sector profiles.** `eu-battery@1` and `eu-textile@1` replace the retired hand-written battery and textile profiles. A product document is validated against its binding's schema, contexts and SHACL shapes, the product is checked against its passport, and the document is split into a public and a restricted part.
- **EPCIS source exchange.** Events are imported from files or pulled from a standard query endpoint, retained byte for byte with their findings, exported unchanged, and moved to another store as an authorised recovery snapshot.
- **Portable evidence and delivery.** Profiles travel in the evidence package. The engines run in-process or as a separate validator service. The index and the validator ship as npm packages and as images, and the operator preset pulls the images by digest.
- **A whole-deployment inventory** with a recorded disposition for every part ([the whole deployment](docs/contribute/licence.md#the-whole-deployment)).
- **EPCIS lifecycle claims.** `dpp-epcis-lifecycle@1` signs one EPCIS event in an envelope that binds it to its passports, and the starter issues lifecycle claims only in that format. Importing an event still signs nothing: an imported event becomes a claim only when an issuer signs it, and never as its observer.

What it does not change: **native `dpp-lifecycle-v1` claims stay readable and verifiable, byte for byte.** Other producers, including any deployed application outside this repository, still issue them, so lifecycle replacement is claimed for the starter only. The selection claims no EPCIS lifecycle claim, and the reference registry does not yet accept the format.

What it waits on before publication: each disposition the inventory lists as open, which `node scripts/deployment-inventory.mjs --release` names. The candidate keeps the version numbers above, none of which is on npm yet.

- The W3C credentials context in `@bsv/dpp-credentials` now ships with the full W3C Software and Document License text and its copyright notice in `artifacts/w3c/NOTICE.md`, and the index image carries `NOTICE` and `PATENTS` beside `LICENSE`. No API changes.
- `managed-custody@2` is the one custody profile: readers read `dpp-managed-acceptance@1` under its direct-signature rule and `@2` under the derived key, and the candidate writes no `@1` record (step 1).
- `signManagedAcceptance` takes the state-signing `DataSigner` in place of the removed `AcceptanceSigner` interface and writes `dpp-managed-acceptance@2` only, signed by the custodian's BRC-42 child for `[1, 'dpp managed record v1']`; the `ManagedAcceptanceClaim` type admits that format alone and `ManagedAcceptanceRecord` admits both; `MANAGED_CUSTODY_PROFILE` is `managed-custody@2`, which the index declares, and `MANAGED_RECORD_PROTOCOL_ID`, `managedRecordVerificationKey`, `MANAGED_ACCEPTANCE_FORMAT_V1` and `MANAGED_CUSTODY_PROFILE_V1` are new (step 2).
- Under `managed-custody@2` each state locks to its own field-6 controller key (`spec/managed-custody.md` §2).
- The owner-signed transfer, `owner-consent@1`, is removed: `checkOwnerConsent`, `OWNER_CONSENT_REFUSALS`, `OWNER_LINKAGE_KEY`, the `ownerConsent` option and `ownerConsentValid` are gone, `ownerConsentPolicy` leaves `@bsv/dpp-overlay/server`, the index drops the `consent-not-proven` refusal and the capability document's `ownerConsent` and `transferAuthorities`, and control authorities default to none (step 7).
- `normaliseTransferAuthorities` is `normaliseControlAuthorities`, the `ChainFailureKind` `consent` is `commitment` and `StateInspection.consentError` is `commitmentError` (step 7).
- The holder instruction record is parked outside the standard: a custodian's `UPDATE` or `RETIRE` for a managed holder after a committed `TRANSFER` depends on custody, and the report's limits say so (step 3).
- The index refuses to boot with `OWNER_CONSENT`, `TRANSFER_AUTHORITIES`, `INSTRUCTION_COMMITMENT` or `EXPORT_SIGNING_KEY` set: recovery keys go in `CONTROL_AUTHORITIES` and the export key in `EXPORTER_PRIVATE_KEY` (steps 3 and 9).
- Record version 3, the token carrier, is parked: the packages read and write versions 1 and 2 only, every version 3 export is gone, and the index drops the `carrier-prefix-invalid` and `token-id-mismatch` refusals and the `tokenId` lookup and declares no `dpp-record` version `3` (step 8).
- The verification report is version 2, without the reason codes `carrier-prefix-invalid`, `token-id-mismatch`, `consent-not-proven` and `resource-limit`; a version 1 report validates under `verification-report-v1.schema.json` (step 11).
- `verifyPassportEvidence` checks each token state's `payload_public` against its declared profile through the policy's `payloadValidator`, which `profilePayloadValidator(ajv)` from `@bsv/dpp-profiles` supplies; the new reasons are `profile-undeclared` and `schema-unavailable` (step 4).
- The `payloadValidator` is told which passport a payload sits in: `DeclaredPayload` gains `passportId`, read from the decoded state and never from the payload, the expected subject or the outpoint, and `PayloadToValidate` in `@bsv/dpp-profiles` gains an optional `passportId` that `profilePayloadValidator` ignores. A validator that ignores it works as before, and no transaction field, record format or signature preimage changes.
- `@bsv/dpp-profiles` recognises a profile defined outside the package and held by an immutable binding, beside the manifest format (`spec/profiles.md` §7, `schemas/profile-binding-v1.schema.json`). `createProfileRegistry({ trustedBindingDigests })` registers a binding only when its digest is trusted, no other binding answers for its `id` and `version`, and every artefact it names matches its recorded byte length and SHA-256; it refuses with a typed code and resolves the supported manifest profiles through the same `resolve(id, version)`. New beside it: `readProfileBinding`, `profileBindingProblems`, `profileBindingInconsistencies`, `profileBindingDigest`, `describeArtefact` and `parseStrictJson`.
- `bindingPayloadValidator({ registry, engines })` in `@bsv/dpp-profiles` has the shape of `profilePayloadValidator` and of the report's `payloadValidator`. For a profile held by a binding it checks the payload envelope (`profile`, `profile_version`, `profile_binding_sha256`, `product`, and the optional `notice`), the binding digest, then the binding's `json-schema`, `json-ld-expand`, `shacl` and `passport-identity` steps. A step that fails is `fail`; a step that could not run, for want of an engine, a capability, time, a registered profile or a passport identifier, is `unknown` and never `pass`. The answer keeps the reason codes `schema-invalid` and `schema-unavailable`, and `PayloadValidation.detail` may now be a `BindingValidationDetail` that names the precise cause and lists every step and SHACL finding.
- `checkProductIdentity` in `@bsv/dpp-profiles` decides whether the product document in a payload is the item its passport is about: the expected identity is the supplied `passportId` alone, the host is not compared, GTIN widths are equivalent, a serial is compared exactly, and a model, a batch, a contradiction or a wrong check digit fails.
- `@bsv/dpp-profiles/validation-engine` is a new entry point: `createValidationEngine` builds the JSON-LD and SHACL engines, with SPARQL constraints, over `jsonld@9.0.0`, `n3@2.13.12` and `shacl-engine@1.1.3`. The caller installs those libraries; the package does not depend on them, its main entry point never loads them and the index image does not install them. The adapter refuses any context it was not handed, fetches nothing and discards a result that arrives after its time limit.
- `@bsv/dpp-profiles` can run the JSON-LD and SHACL engines in another process: `@bsv/dpp-profiles/validator-service` and the `dpp-validator` command serve them under the `dpp-validator/1` contract (`contracts/validator.schema.json`, `spec/services.md` §7), and `createValidatorClient({ url })` from `@bsv/dpp-profiles/validator-client` returns the engines `bindingPayloadValidator` takes, so an application chooses by configuration. The service holds every file a request carries to its SHA-256, fetches nothing and stops an operation that runs over its time limit; a service that is stopped, slow, redirecting or answering anything but the contract reads `unknown`, never `pass`.
- `packages/dpp-profiles/validator-image/Dockerfile` builds an image of that service from a lockfile of its own, with a licence inventory of its 413 packages; the index image and every npm package are unchanged by it, and the image is not published.
- `examples/custom-profile/` holds two example profiles written for this repository, `example-bottle@1` and `example-notebook@1`, with their vectors, and `node examples/custom-profile.mjs` registers them from their folders and checks every vector.
- `@bsv/dpp-profiles` ships two bindings under `bindings/`, `eu-battery@1` and `eu-textile@1`, for battery and textile passport data of one serialised item. Each runs JSON-LD expansion, SHACL with SPARQL constraints and the passport identity check, and only violations block. `BUNDLED_BINDINGS` and `BUNDLED_BINDING_DIGESTS` are the trusted digest list for them, and `registerBundledBindings(registry)` reads them from the package folder, holds each binding file to its pinned digest and registers it; importing the package reads none of the files. The contexts and shapes are definitions published by a third party under Apache-2.0, see the notice beside each binding. Each name states the data model a product document uses and claims no compliance with any law, and `battery@2` and `textile@2` are unchanged ([EU battery and textile bindings](docs/profiles/eu-sector-bindings.md)).
- A binding may state an `access` member: which top-level properties of the product document are public. Every other property is restricted, one the binding does not name included, and nothing is split inside a nested object or a list (`spec/profiles.md` §7). The list is in the binding, so the digest a payload declares commits to it, and a binding that restricts a member the identity rules read is refused as `binding-inconsistent`. `eu-battery@1` lists 46 public properties and `eu-textile@1` 54, so a `payload_public` under either carries the public properties only, and one that carries any other property fails as `restricted-property-disclosed` ([which properties are public](docs/profiles/eu-sector-bindings.md#which-properties-are-public)). A binding without `access` is unchanged.
- `prepareBoundPayload` in `@bsv/dpp-profiles` is the writer's call under a binding: it validates the whole product document, splits it, returns the public payload as the exact text to sign with the restricted part beside it, and holds that text to 65,535 bytes of UTF-8. It refuses with `validation-failed`, `validation-unavailable`, `public-payload-too-large`, `public-view-failed` or `profile-not-bound`, and issues, signs, encrypts and stores nothing. `splitProductByAccess` and `assembleProduct` cut and rejoin the two parts on their own, and a rejoin refuses with `part-not-an-object`, `join-key-missing`, `restricted-part-names-another-product`, `property-in-both-parts`, `restricted-property-in-public-part` or `public-property-in-restricted-part`.
- `bindingPayloadValidator` reads a public payload under a binding with `access` as a projection of the whole document. A rule that misses only a restricted property is withheld, not failed, and any withheld rule makes the answer `unknown` with the cause `restricted-tier-withheld`, never `pass`. `authorisedPayloadValidator` is new: it takes the public payload and the restricted part, rejoins them and runs every step on the whole, and parts that do not rejoin fail as `product-assembly-refused`. `BindingValidationDetail` gains `access`, with the view checked and the withheld rules, and the steps `access` and `assembly`. Neither view compares a restricted part with a record's `payload_owner_hash`: that stays the protocol's check, and a pass or a rejoin is no evidence of it.
- `@bsv/dpp-profiles` carries a profile held by a binding inside a `dpp-evidence-package@1`, as a profile bundle (`spec/profiles.md` §7, `spec/portable-evidence.md` §2, `schemas/profile-bundle-v1.schema.json`). `exportProfileBundle({ registry })` returns the files and the inventory entries: each binding in its exact bytes, every artefact it lists with its media type, length and SHA-256, the notices it lists, the licence texts given and a descriptor, `profile-bundle.json`. The entries use the existing `schemas` category with `represents` and `representation`, so the package manifest, its schema and `@bsv/dpp-protocol` are unchanged. A file GS1 publishes, or one whose digest the exporter lists as `provisioned`, is named by address, SHA-256 and length and is never carried. An export is refused as `notice-unavailable` when a notice a binding lists cannot be read.
- `openProfileBundle` reads a bundle from memory (`profileBundleFiles`) or from a folder (`profileBundleDirectory`), and `registerProfileBundle(registry, bundle)` registers its profiles through the destination's own registry. Trust stays the destination's list of binding digests: a package that its exporter signed correctly and that carries another binding under a known profile name is refused as `bundle-binding-untrusted`, or as `bundle-binding-substituted` where the destination holds or expects a digest for that profile, and an artefact that is not the file the trusted binding records is refused as `bundle-artefact-altered`. A bundle that lacks a listed file is `bundle-artefact-missing`, a file the destination was to supply is `bundle-artefact-not-provisioned`, and a refused profile validates as `unknown`, never `pass`. The descriptor states in fixed words that a bundle carries bindings only, that the destination decides trust, and that validation under a carried profile says nothing about `payload_owner_hash`.
- `BindingProfile`, what a registry returns for a profile held by a binding, gains `bindingBytes`: the binding file's exact bytes as registered. A `ProfileRegistry` you implement yourself must return it. `bundledBindingNotices()` and `bundledBindingLicenceTexts()` supply the `NOTICE.md` of each bundled binding and the licence text it points to, for an export.
- `node examples/portable-profile.mjs` exports the two example profiles into a signed package, switches the network off, restores them into a second registry from the package folder and gets the same answer for every payload vector, then shows the refusals.
- `checkBindingUpdate({ active, candidate })` in `@bsv/dpp-profiles` is the binding update check (`spec/profiles.md` §7): given the active version of a profile held by a binding and the files the next version would list, it returns a change report and a proposed binding at the next version with a digest of its own. The report lists every file as added, removed, changed or unchanged with both lengths and digests, and for a JSON-LD context each term added, removed or redefined, the last two marked as breaking, as is a listed context it no longer names; every other file is compared by digest only, and the report says so. It registers nothing, fetches nothing, runs no vector and leaves the active version byte for byte as it was, and the proposal registers only where its digest is trusted and never over the version it came from. `node examples/check-binding-update.mjs` walks through it, and takes a binding folder and a candidate folder of your own.
- A native claim names its state by outpoint, `<txid>:<outputIndex>`, in `recordId` and carries no `evidence` property; `signLifecycleClaim` and the registry contract refuse anything else (step 4). `verifyLifecycleClaim` still reads a claim signed before that rule, whose `recordId` is the transaction identifier alone, so claims already issued keep verifying.

- Acceptance records travel in evidence packages under `authority`, keyed by commitment, and `acceptanceRecordsInPackage` reads them back (step 3).

- `@bsv/dpp-credentials` no longer carries the parked VSC profile, its Ed25519 and BBS suites or the `epcis-vsc@1` and `epcis-vsc@2` mappings, and `./epcis-source` loses `readEpcisSourceReference` and `EPCIS_MAPPING_PROFILES` (step 6).

GS1 publishes these files under its own terms, and this repository and its packages do not redistribute them: each deployment obtains them from GS1 and the package checks every byte against a pinned digest. - `fixtures/vectors/dpp/epcis-lifecycle/v1.json` pins the new claim's vectors: all five event types, the representative lifecycle cases and the refusals.
- The application `@bsv/create-dpp-app` generates issues lifecycle claims only as EPCIS lifecycle claims, `dpp-epcis-lifecycle@1`, from an EPCIS event a member enters on a passport's page or one its EPCIS exchange retained, which is signed exactly as received with a source link to the import and never as the observer. The bindings come from the event's identifiers matched to the application's passports under the identity rules, class references at class level only. `POST /api/passports/:ref/claims` takes `event`, `imported` or `correctionOf` and refuses a body with `eventType` as `four-category-claims-retired`; sending to a registry, which anchors the claim once per bound passport, stays a separate step ([lifecycle claims](docs/packages/create-dpp-app.md#lifecycle-claims)).
- In the same application `GET /api/passports/:ref/claims` answers `{ lifecycle, historical, discovery }`: EPCIS lifecycle claims found by the index's anchors and the application's records, each verified, with every finding on its own and a passport's part in the event decided by its verified bindings, never by an anchor's subject; and the native `dpp-lifecycle-v1` claims it issued before, verified under their own rules and labelled historical. `GET /api/lifecycle-claims/:id` returns a claim's exact bytes, the export carries them under `application/lifecycle-claims/`, and a restore verifies them before it writes. Its in-process index admits generic anchors on `tm_attestation`.
- Native claims are unchanged. Other producers of `dpp-lifecycle-v1`, including any application deployed from an earlier starter, still issue it until they change, and a reader keeps verifying it; lifecycle replacement is claimed for the starter only. The selection still claims no EPCIS lifecycle claim.
- `packages/dpp-protocol/test/historical-lifecycle.test.ts` holds `fixtures/attestation-anchor-v1.json`, `fixtures/battery-lifecycle-v1.json`, `fixtures/vectors/dpp/attestation-anchor/v1.json` and `examples/lifecycle-v2.mjs` to their published bytes and verifies every native claim in them under its own rules.
- `verifyEpcisLifecycleClaim` is stricter in four places, each stated in `spec/epcis-lifecycle-claim.md` and held by new vectors. A claim whose signature does not pass or whose event structure fails names no item participant (§5). An error declaration counts only when the declaring claim is itself sound; one that is not leaves the correction state `unknown` with `x-declaration-unsound` (§7). An event that uses an extension term while the claim lists no extension rule has its semantics `unavailable` (§4). Each passport is judged on the anchors that name it, the passport the caller expects when it names one, and an anchor about any other subject changes no finding (§8).
- `GET /capabilities` of the index declares `dpp-epcis-lifecycle-json@1`, the representation the starter anchors on `tm_attestation`, and no longer declares the parked `epcis-event-vc@1`. The declaration gates nothing: an anchor of any representation is admitted and found as before.
- `signLifecycleClaim` is marked deprecated in favour of the EPCIS lifecycle claim. It is unchanged and is kept, with the native format, for reading historical claims.
- The `@bsv/dpp-credentials` archive no longer carries the build output of the parked signed-event module, which no entry point loads.
- `scripts/deployment-inventory.mjs` recognises the full W3C licence text by its clauses, so the `w3c-context` disposition reads `held`.
- A registry serves the one capability document at `GET /capabilities`. The registry contract, still `0.6.0`, drops the document of its own that no registry could serve together with the one `spec/conformance.md` §4 requires: a registry now declares `capabilitiesVersion`, `implementation`, `roles`, `protocols`, `profiles` and `anchorFormats` under `contracts/capabilities.schema.json`, names `tm_attestation` under `topics` and `ls_attestation` under `services`, lists each representation as an object, and names its anchoring key under `publisherPolicy.anchoringServices` and `exporterIdentityKey` in place of `anchoredBy`. The schema gains the optional `interoperability` member, which a registry declares unchanged, and `conformance/examples/capabilities-registry.json` is an example. An index's document does not change. The reference registry still serves the earlier document ([registry](docs/implement/roles/registry.md#the-minimum-a-registry-serves) lists every member).
- The application `@bsv/create-dpp-app` generates reads a claim's bytes from `securedBytes` of the registry's `GET /attestations/{id}/proof`, the member the registry contract gives them, where it read `envelope`, which that route does not carry, and so found no bytes at a registry that follows the contract.
- The same application reports a registry's refusal of a claim by the contract's `outcome` and first of its `issues`, as in `invalid: <issue>`, where it read `description`, which the contract does not define, and showed nothing.
