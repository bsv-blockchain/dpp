# GS1 discovery

**Profile: `gs1-digital-link@1`. Status: proposed, pre-1.0.** This document defines how a passport identified by a GS1 Digital Link URI is resolved to its passport and evidence services: the grammar the profile reads, the identity rules that survive resolution, what a resolver under this profile does and does not do, what a discovery client may conclude from a linkset, and how the older evidence route is kept. It binds `packages/dpp-profiles/src/gs1-resolution.ts` and `gs1-epc-binary.ts`, the manifest `packages/dpp-profiles/manifests/interoperability/gs1-digital-link@1.json`, the pinned GS1 artefacts under `packages/dpp-profiles/schemas/gs1/` and the vectors under `fixtures/vectors/dpp/interoperability/gs1/`. It changes nothing about the passport identifier itself, which [`record-model.md`](record-model.md) §3 and [`profiles.md`](profiles.md) §5 define, and nothing about credential subjects, which stay exactly as signed.

## 1. Scope

The profile hosts one primary key, the GTIN under application identifier 01, with every key qualifier the URI syntax gives it: the consumer product variant (22), the batch or lot (10) and the serial (21), in that order, in every combination the syntax permits, together with data attributes in the query string. It decompresses the special compressed form that carries an EPC binary string, for the SGTIN-96 and SGTIN-198 schemes, because a GS1-Conformant Resolver must (GS1-Conformant Resolver 1.2.1 §2.3). It claims the resolver standard's clauses for that scope and declares the scope in its resolver description file. It does not host any other primary key, the third-party serialised extension (235), or the general GS1 Digital Link compression algorithm, and it refuses each of those by name rather than reading it as something it is not. The normative texts are GS1 Digital Link: URI Syntax 1.7.0, GS1-Conformant Resolver 1.2.1 and GS1 Digital Link URI: Compression Technical Standard for EPC binary strings 1.0.0, with the EPC Tag Data Standard for the two schemes; the manifest records which sections are claimed and which artefacts are pinned.

When `passport_id` is a GS1 Digital Link URI ([`record-model.md`](record-model.md) §3), the host it is minted under SHOULD be a GS1-Conformant Resolver for primary key 01 under this profile, answering every path under `/01/` as section 4 says; a host that is not one SHALL answer every path under `/01/` with 307 Temporary Redirect to the same path and query string under a resolver that is. The resolver standard names no status code for a redirect, so 307 is this profile's choice; passing the whole query string on follows resolver standard §2.12. The resolver either implements section 4, which the helpers in `@bsv/dpp-profiles` provide, or is an external GS1-Conformant Resolver, which the discovery client reads through the same contract. A resolver never shares an origin with a route that answers `/01/` paths under another contract, such as the legacy evidence route of section 4. Nothing in this document requires an application account, a wallet or a DID of anyone who scans a code.

## 2. Identity

A GS1 key tuple is the primary key and its qualifiers with their values: `01:09521234000013|10:LOT-2026-01|21:SER-0001`. Two Digital Link URIs under different hosts, stems or GTIN spellings that reduce to one tuple name one identified entity, and `sameGs1Key` says so; the same serial under a different GTIN is a different tuple and is never joined. A URI's check digit is reported, never enforced on reading, because historical records carry GTINs that fail it; a writer never publishes one that does (`profiles.md` §5). Syntax, a correct check digit, a decodable EPC, a resolvable DID or ownership of a host prove nothing about who GS1 allocated a number to, and nothing in this profile infers allocation authority.

A resolution record MAY carry the exact signed passport identifier bound to its entity, with a reference to the evidence or policy that established the binding, when the binding is established; it never derives one from the key. Tuple equivalence is not that evidence. A signed credential's subject identifier stays exactly as signed; a linkset anchor is the resolver's uncompressed spelling of the request and does not rename anything. An EPC URN carried in an event is translated to a key tuple only by the decoding rules of the Tag Data Standard, never by guessing a company-prefix length from digits; an identifier under another scheme keeps its scheme, and an `https` identifier is not called a GS1 key because it looks like one.

Decompression establishes what the bits say and no more. It yields the uncompressed URI under the stem the compressed form carried, the key tuple, the filter value and the pure-identity EPC URI, and it refuses any EPC scheme outside the two it implements with the header named.

## 3. The grammar

`parseGs1DigitalLinkUri` reads a request URI and answers with one of three kinds, never with an exception:

- `uncompressed`: the origin and stem, the fourteen-digit GTIN with its check-digit and demonstration-prefix findings, the qualifiers in order, the data attributes each marked `validated` true when this profile knows the AI's format and it held or false when the AI is carried unvalidated, the `linkType` request (a `gs1:` CURIE expanded to the GS1 vocabulary, a full IRI kept, `linkset` or `all` as the list request, anything else unexpanded), and every other query parameter preserved for forwarding.
- `compressed`: the stem, the prefix `eh` or `ex` and the compression string, for `decompressGs1DigitalLink`.
- `invalid`: one reason from a fixed list (`not-a-url`, `scheme`, `percent-encoding`, `no-primary-key`, `unsupported-primary-key`, `primary-key-not-a-gtin`, `trailing-segment`, `qualifier-order`, `qualifier-repeated`, `qualifier-unsupported`, `qualifier-value`, `key-in-query`, `attribute-value`), which a resolver answers with 400 (resolver standard §2.4.1) and a client records as a finding.

One trailing slash is tolerated (§2.13). A qualifier value is one to twenty characters of the GS1 encodable set 82, percent-decoded. A key or key qualifier in the query string is refused: it belongs in the path. An unknown data attribute is carried, not refused, so a new AI does not break a resolver built before it (§2.4).

## 4. The resolver

A resolver under this profile serves its configured origin, which is the identifier host wherever that host resolves (section 1), and publishes its description file at `/.well-known/gs1resolver` as `application/json`, built by `describeResolver`, naming `01` as the only supported primary key, the GS1 vocabulary and this standard's link namespace, `linkset` never the default, and the pinned GS1 context for JSON linksets (§3). The description file is published only by an origin that actually provides the resolver contract; the legacy API origin does not describe itself as one. It answers GET, HEAD and OPTIONS over TLS (§2.2). Every answer at the description file and under `/01/`, a redirect or an error included, carries `Access-Control-Allow-Origin: *` with GET, HEAD and OPTIONS allowed, and `Vary: Accept, Accept-Language`. Forwarded host headers are checked against the configured origins rather than trusted. The reference registry implements this section with the published helpers on a resolver origin of its own, except the header rule: its answers to OPTIONS, to a path that is not valid percent-encoding and to an internal error do not yet carry `Vary`.

Resolution records are validated when written, not on every request (§2.4): `resolutionRecordProblems` refuses a failing check digit, qualifiers out of order or repeated, the third-party extension, a serial registered beside a variant or a lot (§2.5.10), more than one default link for an entity, a default carrying optional attributes (§2.5.8), a target that is not `https`, a missing title, a relation the linkset schema cannot carry, an undeclared disclosure and a malformed language tag or media type. Writing a record requires scoped operator authority over the configured namespace, which the resolver's operator enforces; it is never inferred from a check digit, a DID, a URL or an application account.

For a request, `matchRecords` selects records by the union rule of §2.5.10, most specific first: the serial level, the variant-and-lot level, the lot level, the variant level and the GTIN level, each only when the request carries the qualifiers that level names. Every matched record keeps its own anchor, the uncompressed URI of the record's identifier under the resolver root, and its own granularity (`model`, `variant`, `lot`, `item`). A link found at the GTIN level under a serialised request is served with the GTIN anchor and the granularity `model`: it is broader information the item inherits, and it is not evidence that an item passport, a batch membership or an item measurement exists.

`resolveLinks` then answers as the standard's flow chart does. With no `linkType`, the most specific matched record that registered a default answers with 307 Temporary Redirect: to a refined default (`gs1:defaultLinkMulti`) when exactly one matches the request's media type, language or context better than the others, else to the single default (`gs1:defaultLink`), so there is always a definite answer (§2.5.8, §2.6.1). With a `linkType`, the links of that relation across every matched level are ranked by media type, then language, then context, in the client's own preference order, with a link that makes no claim outranking one that contradicts the request; a unique best is a 307 redirect, an unresolved tie is 300 Multiple Choices with the candidates, and no link of that type is 404 with the available links beside it (§2.6.2, §2.6.3). `linkType=linkset` or an `Accept` of `application/linkset+json` never redirects: it is answered 200 with the linkset (§2.9). A syntactically valid URI nobody registered is 404 with nothing beside it; a syntactically invalid one is 400; an error is never a 200 (§2.4.1). A resolver MAY answer an error with an HTML page for a client that asks for `text/html`, and that page keeps the 400 or 404 status. On a redirect the resolver forwards the request's query string to the target (§2.12) unless the link declares `forwardQuery: false`; a redirect never places a bearer credential in a URL.

`linksetDocument` builds the list (§2.10): one link context object per matched record, most specific first, its `anchor` the uncompressed URI, each link under its full-IRI descriptive relation and a default additionally under `gs1:defaultLink` or `gs1:defaultLinkMulti`, `hreflang` and `context` as arrays, and the document validating against the pinned linkset schema. The JSON response carries a `Link` header to the pinned GS1 context under the relation `http://www.w3.org/ns/json-ld#context`. The passport page a person reads is a link target, not the resolver's answer: where the identifier host resolves, the page lives at a URL of its own, never at the identifier's path, and the item's serial-level record names it under `gs1:dpp` as the single default, so a browser that opens the identifier, from a printed code or any link to it, reaches the page through the 307 of the default response. A linkset request that prefers `text/html` MAY be answered with an HTML page presenting the same links (§2.10); it is never the passport page.

Link relations are full IRIs of the GS1 vocabulary, expanded from `gs1:` as the resolver standard's text does; the published linkset context spells the same namespace differently, and the reference code reads both. Where the GS1 vocabulary has no term, the relation `https://dpp.bsvb.net/link/evidencePackage/1` names a passport's portable evidence package ([`portable-evidence.md`](portable-evidence.md)); it is spelled without a hyphen because the pinned linkset schema admits an IRI key only as letters, digits, dots and slashes. A configured `gs1:epcis` link names an actual EPCIS service or standard query resource; the application's import store is never advertised as one.

A resolver that serves an identifier host, at that host or as the target of its redirect (section 1), holds, for each passport it answers for, a serial-level record carrying the passport page under `gs1:dpp` as its single default and, where the resolver can name one, the passport's evidence package under `https://dpp.bsvb.net/link/evidencePackage/1`, each link public, and a GTIN-level record carrying exactly one single default, such as a model or product page under `gs1:pip`, so that every request under that GTIN has a default at its own level or above (§2.5.9). Because a request walks up to that default, its target is not itself a GS1 Digital Link URI: §2.5.9 says a resolver SHOULD NOT redirect a more granular request to a less granular one, so a product page lives at a path such as `/product/<gtin>` rather than one carrying `/01/`. It MAY synthesise these records on request from data it already holds instead of storing them, provided each record it answers from is one `resolutionRecordProblems` admits.

Disclosure is a property of every link. A public audience is never returned a restricted link, in a redirect, a 404's list or a linkset, and the refusal wording does not reveal that one exists; an authorised audience is returned it flagged `public: false`, and access is enforced again at the target. Public discovery never enumerates protected records. Every answer varies on `Accept` and `Accept-Language`, as above; a public linkset MAY be cached for a bounded time under a key that includes the identifier, the configuration revision and the audience, and a response to an authorised audience is private and never stored as a public representation.

The compatibility route is kept. The legacy evidence JSON that the API origin answers at `/01/{gtin}/21/{serial}` continues unchanged, and `/resolve/gs1/01/{gtin}/21/{serial}` is an explicit alias of it (`legacyEvidencePaths`). That JSON is not a linkset and does not claim a `linkType`; the resolver origin's linkset is a different document with a different contract. Moving the resolver onto the API origin later needs client updates and an explicit negotiated compatibility before the old default changes.

## 5. The discovery client

A client reads the resolver description file, checks that its `resolverRoot` is the origin it was configured to use and that `01` is a supported primary key, requests the linkset for the identifier, validates it against the pinned schema and selects with `selectLink`: the links under the requested relation (a full IRI or a `gs1:` CURIE) across every link context object, ranked as the resolver ranks, answered as one link with its anchor and the anchor's scope, as ambiguous with the candidates, or as not-found with the relations that are available. The anchor's scope is the parse of the anchor: a link found under a GTIN anchor is model information, whatever the client asked about, and an anchor the client cannot read as a Digital Link URI has scope `unknown` and is not guessed. The client hands the selected endpoint to an explicit consumer; the caller's policy decides whether the network is reached at all and with what credentials, and nothing in a linkset establishes issuer authority, the passport's current state or a global latest state.

Section 1 makes an identifier's resolver either its own host or the resolver that host redirects `/01/` paths to. The client is configured with that resolver's origin and reaches no other, so it does not follow a redirect from the identifier host to another origin. A client MAY use an external GS1-Conformant Resolver through the same reading; a resolver built on this profile is one choice, not a requirement. Party, location, asset and component references met in a linkset or an event are preserved as the identifiers they are, without claiming that this profile hosts their keys.

## 6. Normative and implementation

What a conforming party reproduces: the identifier-host rule (§1), the grammar and its refusal reasons (§3), the key-tuple rule and the binding rule (§2), decompression of the EPC binary form for the two schemes (§2, §3), the registration rules, the union rule, the default and matching rules, the identifier-host records, the status codes and headers, the linkset shape and the disclosure rule (§4), and the client's reading of a linkset with its anchor scope (§5). What is a build's own: whether its identifier host resolves or redirects to a resolver, how records are stored, administered or synthesised, the cache lifetimes, the passport page's URL and content and any HTML error or linkset page, and whether an external resolver replaces its own.
