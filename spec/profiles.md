# Profiles and identifiers

**Status: working draft, pre-1.0.** This document defines what a profile is, how one is published, versioned and selected, how a payload is checked against it, how a profile defined elsewhere is held by a binding, and how the identifiers a passport carries relate the model, the batch and the item. It binds the industry data profiles this repository publishes in `packages/dpp-profiles`, and it is the rule an application or registry follows when it consumes them. The record model fixes what a state is; this document fixes what its public payload is expected to say under a named profile.

## 1. What a profile is

A profile is a named, versioned selection over the core. Four kinds exist, and a profile is exactly one of them. An **industry profile** selects the fields a passport's public and restricted tiers carry for one kind of product, their meaning, units, code lists, granularity, provenance and access, and the obligation source behind each. An **exchange profile** selects a credential format, its schemas, contexts and proof suites, and the mapping to and from native evidence. An **operator profile** selects admission, discovery, synchronisation and retention behaviour for a service; the named operator profiles the reference index package declares are that package's own, documented with it ([`services.md`](services.md) §6). A **custody profile** selects who holds a passport's keys and what a transfer must commit to, such as `managed-custody@2` ([`managed-custody.md`](managed-custody.md) §7). The four are distinct selections and a deployment declares each it makes; none implies another.

A profile MUST name its use case, the baseline it requires, the roles it binds, its dependencies, the combinations it is incompatible with, the options it selects and the acceptance vectors that exercise it. Where one named, tested choice would do, a profile makes the choice rather than adding a switch.

## 2. The profile manifest

An industry profile is published as a manifest conforming to `packages/dpp-profiles/schemas/profile-manifest.schema.json`. The manifest is the canonical definition; every form, validator, consumer document and registry endpoint is generated from it, and nothing that consumes it edits it. An industry profile whose definitions are written outside a manifest is held by a binding instead (§7).

| Property | Requirement |
|---|---|
| `id`, `version` | The profile identifier and a positive integer version; together `general@2`. Once published under a version, a manifest is immutable. |
| `status` | `draft`, `current` or `superseded`, with `supersededBy` on a superseded manifest. A superseded manifest remains published and served for as long as any state declares its version. |
| `schemaUri`, `schemaDigest`, `schemaDialect` | The JSON Schema generated for the profile's public payload, its SHA-256 and its dialect, which for every artefact published under this document is JSON Schema 2020-12. A consumer refuses a dialect it does not implement and never infers one. |
| `contextRefs` | Semantic contexts and vocabularies the field meanings resolve into, each pinned by identifier and version. |
| `extends` | The manifest this one extends, if any; a field the extension does not restate is inherited unchanged. |
| `fields` | §3. |
| `eventMappings` | The conditional mappings from native operations to lifecycle event semantics under this profile ([`rules.md`](rules.md) §2), each with its evidence condition. |
| `accessPolicyRef` | The access policy the tiers refer to. |
| `sourceRefs` | Every regulation, standard, vocabulary and register the manifest cites, with version, licence and how it is used; licensed texts are cited by clause and never reproduced. |
| `applicability` | The product categories, jurisdictions and dates the profile is intended for, with each legal statement marked `enacted`, `anticipated` or `needs-review`. |

**Manifest version 2.** A profile that needs the shared shapes or the composable rules of §3 publishes its manifest under version 2, conforming to `packages/dpp-profiles/schemas/profile-manifest-v2.schema.json`. Everything version 1 declares survives unchanged, so a reader of version 1 reads every field it knows. Version 2 adds, per field, a `requirement` whose `status` says what asks for the value (`enacted`, `guidance`, `anticipated`, `needs-review`, `not-to-be-displayed` or `none`) and names its source, clause and effective date, separate from the profile's `obligation` and from `legalBasis`; a composable `applicability` rule (§3); a `precision` for date fields; a `scope` and `componentScoped` for component facts; and an `overridable` declaration naming the granularity and policy under which a finer source may take precedence. The six shape value types of §3 join the value types. A manifest may carry `succession`: the version it follows and, for every changed field, the migration outcome (`unchanged`, `renamed`, `retyped`, `split`, `new`, `withdrawn` or `relabelled`) with a note.

## 3. Fields

Each field states a JSON pointer into the public or restricted payload, a semantic URI where one exists, a value type, its unit or code list, its cardinality, the granularity it describes (`model`, `batch` or `item`), the provenance the value must carry, and its access tier. Its `obligation` is `required`, `recommended` or `optional`, and is a separate property from `legalBasis`, which cites the instrument that asks for the value or says plainly that none does. Where an obligation holds only under a condition a form cannot decide, the field carries a machine-evaluable `applicability` expression where one can be written, and otherwise the word `needs-review`; a consumer MUST NOT read `needs-review` as satisfied or as universally required. Under manifest version 2 the expression is one of the composable rules `always`, `category-in`, `jurisdiction-in`, `effective`, `threshold`, `all`, `any`, `needs-review` and `unresolved`, and its evaluator answers `applies`, `not-applicable` or `unresolved` and never a fourth word. `unresolved` is never satisfied and never a failure: an unresolved required field is shown, does not block a draft and cannot pass as settled compliance until the record supplies the value or declares it inapplicable under `inapplicableFields`. A field whose requirement status is `anticipated`, `needs-review` or `not-to-be-displayed` is never schema-required and never counted as missing, because a validator must not demand what guidance says not to fill.

Constraints are resolved, never implied: a percentage carries its bounds, a country carries its pattern, a closed list says it is closed. A list the source has not closed is `open`, and a value outside it is valid. A value whose permitted form waits on an act not yet adopted says so under `awaitingAct` and states no list or pattern; a consumer does not reject a value for such a field. A field marked `prose` is one a person writes for a person to read, by decision.

The access tiers are `public`, `owner`, `legitimate` and `authority`. `public` fields go on chain in `payload_public`. The other three form one restricted object, committed once as the owner tier of [`record-model.md`](record-model.md) §7 and disclosed per tier by re-encryption to the entitled reader. An `owner` field reaches the owner alone. A `legitimate` field may also reach the parties with a legitimate interest and the authorities the manifest's `accessTiers` describes. An `authority` field reaches only the owner and those authorities. A disclosure to an authority may therefore carry the `legitimate` fields as well, and a disclosure to a party with a legitimate interest never carries an `authority` or `owner` field. The restricted schema the package generates covers the three tiers together, which is the object the owner encrypts; a disclosure is a subset of it and is checked against the same schema with the withheld fields absent.

JSON Schema validity is one check. Unit conversion, role evidence, provenance and legal applicability are separate checks and a report names them separately ([`verification.md`](verification.md) §4, `schema`). A payload that carries a field the manifest does not declare is preserved in the archived original and excluded from a public projection unless the selected profile permits unknown fields; it is never silently deleted from what was signed.

A value that is more than a scalar takes one of the shared shapes of [`../contracts/profile-evidence.schema.json`](../contracts/profile-evidence.schema.json), which a version 2 manifest names as the field's value type. None of them is a credential format and none makes a value true.

| Shape | What it fixes |
|---|---|
| `claimEvidence` | Which field, which subject, which source revision, credential or document, who reported it, when it is relevant and in which report it was evaluated. |
| `certification` | The scheme and version, certificate identifier, issuer, subject, validity with its precision, the document or credential, and a verification result whose `unknown` is not a pass. A scheme homepage or an issuer signature alone never proves a certification valid. |
| `measurement` | The property, value, unit, basis, functional unit or denominator, method and version, boundary, conditions, time with its precision and subject. A textual value carries a basis. A fraction is not a percent; a mass-balance share is not a physical share. A conversion, where made, is recorded with its source unit and rule and is never implied. |
| `relatedDocument` | A reference, purpose, URL, media type, language, revision, date with precision, and, only for retained bytes, a digest and length. A URL is where a document was seen, not a commitment to its content. |
| `localisedText` | Values by BCP 47 tag. A text is returned in the exact language asked for, else its base language, else the declared default, and the returned language and selection are recorded; a text in none of them is unsupported, never rewritten. |
| `warrantyTerms`, `warrantyExpiry` | A model's duration and calendar rule; an item's derived expiry from an evidenced start at the start's precision. Terms alone yield no expiry. |

A date carries its precision, `day`, `month` or `year`, each with its own pattern, and a month is never given a day. The helpers `datePrecisionOf`, `selectLanguage`, `deriveWarrantyExpiry` and `convertMeasurement` in `@bsv/dpp-profiles` implement these rules and refuse, with a reason, everything they cannot decide.

## 4. Versions, freezing, retirement and migration

`general@2` and the superseded `general@1` are frozen at the digests `packages/dpp-profiles/frozen.json` records, together with every retired profile named below. A frozen manifest changes only by publishing a new version. Every field declares what its value is: a recorded `fact`, the maker's `declaration`, a `calculation` from other fields, or a third party's `assessment`; a consumer never upgrades a declaration to a fact or an assessment to an accreditation by the presence of a signature, because a signature proves who said a thing, and accreditation is a separate, named authority the field's profile or the applicable exchange profile requires and a verifier confirms under `issuerAuthority`. A corrected mandatory field, a changed meaning or an incompatible validation rule is a new version; a state decodes under the profile version it declares and is never reinterpreted under a newer one. Migration is a newly issued state or projection that names its sources; anchored history is never rewritten.

Industry profiles version independently of the core standard and of each other, and a profile's canonical definition lives in this repository from the moment it joins. A profile that depends on another names the exact version it depends on.

A successor to a frozen profile is published first as a draft under manifest version 2 (§2). A draft is frozen at its own digest beside the version it succeeds, is selected only by its explicit version, and is never what a deployment gets by asking for the current version; a conformance claim rests on the current version, and a combination check refuses a claim on a draft (`industry-draft`). Every field of a draft carries a `requirement` (§2), and only an `enacted`, `guidance` or `none` requirement that is `required`, always applicable and captured at registration is required by the generated schema; an `anticipated` requirement never blocks a record. The draft's `succession` block gives one migration outcome per predecessor field with the reason, so a reader knows what changed and what did not. Publishing a draft is additive: it adds entries to `frozen.json` and moves no digest already frozen. The cutover is a later, reviewed refreeze that records the successor as current and marks the predecessor `superseded`; until then the predecessor's digest, generated schemas and contexts stay exactly as frozen. No draft is open today.

**Retirement.** A profile is retired when this standard stops supporting it and publishes no successor under its identifier. Retiring a profile changes what a conforming party does with it. It changes nothing the profile says.

1. A retired identity, an `id` with its `version`, is never reused and never reinterpreted. No manifest and no binding is published or registered under it again, and no other definition answers for it.
2. Its frozen definition is kept. The manifest and every generated file stay published byte for byte at the digests `frozen.json` records. A retired manifest keeps the `status` it was frozen with, because the file is immutable: the list of retired profiles says a profile is retired, and that member does not.
3. A writer MUST NOT issue a state or a claim that declares a retired profile, and MUST NOT prepare or validate a payload for writing under one. This holds for every operation, a state that would carry an earlier payload forward included.
4. A reader MUST report a payload that declares a retired profile as unsupported: `unknown` with `schema-unavailable` under the `schema` check of [`verification.md`](verification.md) §4, with a cause that names the retirement. It MUST NOT pass the payload, and MUST NOT fail it against the retired schema, because the profile's rules are no longer applied. A registry that is asked about a retired identity says that it is retired, which is a different answer from unknown. Every other check is made as for any state.
5. Retirement converts nothing. A signed state or claim under a retired profile keeps its bytes and the meaning it was signed with. Data moves to a replacement only as a newly issued passport under that replacement, written from the product's own data.

These rules bind writers, readers and profile registries. An index does not judge profiles: it admits a state on its structure, its signatures and its lineage ([`services.md`](services.md) §2), and never on the profile its payload declares. A state that a writer issues under a retired profile against rule 3 is therefore indexed like any other, and a reader reports it under rule 4.

The sector profiles first published as manifests are retired from 14 November 2026. Each is replaced by a profile held by a binding (§7), which is another data model under its own identifier and not a later version of the retired one. Nothing converts a payload from one to the other, and no reader applies a retired profile's rules.

| Retired manifest | Binding named at retirement | Binding for new sector issuance |
|---|---|---|
| `battery@2`, `battery@3`, `battery@4` | `eu-battery@1` | `eu-battery@2` |
| `textile@1`, `textile@2`, `textile@3`, `textile@4` | `eu-textile@1` | `eu-textile@2` |

A writer using these sector bindings MUST use version 2 for new issuance. A reader MUST resolve each existing state against its declared edition and digest. A maintenance operation on an existing version 1 passport retains its original binding. Each successor adds a required class for the identified product under §7.

`general@1` and `general@2` are not sector profiles and are not retired.

## 5. Identifiers

A passport identifier names the enduring product record and never changes across the chain ([`record-model.md`](record-model.md) §3). Around it a profile distinguishes three granularities: the **model** a manufacturer designs, the **batch** or lot a production run produces, and the **item** one physical unit is. A field says which it describes, and a manifest may declare the parent relation between an item's identifier and its model's, and between a batch and its model, so a reader can find the model facts an item inherits without those facts being repeated in every item state. The historical passport identifier and the genesis outpoint are preserved through every migration.

Where the identifier is a GS1 Digital Link, the rules of the record model and the GS1 general specifications apply: the GTIN under application identifier 01 is written at fourteen digits with a correct check digit, allocated under a prefix the writer holds or, for a record describing no real object, under the demonstration prefix 952, and the serial under application identifier 21 identifies the item. `packages/dpp-profiles` provides the check-digit and grammar helpers a writer uses to keep that promise. Syntax and a correct check digit never prove allocation authority, which GS1 settles at allocation and a reader cannot see from the digits.

The digits tell software that a record is a demonstration; the `notice` stamp every manifest declares tells a person. A record that describes no real product, such as one whose GTIN is under the demonstration prefix 952, SHOULD carry `notice` as the first property of its public payload: one sentence, in the language of the record, saying that it is a demonstration and that no real product stands behind it. A record about a real product MUST NOT carry `notice`, because a reader takes it as the statement that the product is not real. A reader SHOULD show `notice` wherever it shows the record's product data, before that data, and never as a finding of its own checks.

The resolver location, the host a Digital Link is minted under and any link set a resolver answers are mutable service metadata. A provider change alters where the identifier is answered, never the identifier, the genesis or the history; a profile's data-carrier tests exercise persistent identity across such a change.

## 6. Generated consumers

An application's field registry, its forms and its payload validators, and any profile endpoint a registry serves, are generated from the manifest by a deterministic generator, and a test in each consumer holds the generated artefacts identical to what the generator produces from the pinned manifest digest. Two consumers of one manifest therefore agree field by field, and drift is a red test rather than a support case. For a version 2 manifest the generator embeds the shape definitions into every payload schema that uses one, patterns a month-precision date as a month and carries the version 2 keys in the consumer document. The legacy consumer document (`packages/dpp-profiles/generated/consumer/`) is one such generated projection. So is the field mapping inventory of each current profile (`packages/dpp-profiles/generated/mapping/`): one row per field with its external semantic field or `not mapped`, type and unit or list, granularity, obligation, legal basis, applicability, access tier, capturing party and required evidence, with `needs review` wherever no generator can decide and no legal conclusion drawn.

## 7. Externally defined profiles

An industry profile whose data model is defined outside a manifest, by a JSON Schema, JSON-LD contexts or SHACL shapes of its own, is held by a **binding**: one JSON file per profile version, conforming to `packages/dpp-profiles/schemas/profile-binding-v1.schema.json`. The manifest format of §2 is unchanged. Both formats answer through one registry, so a consumer asks for a profile by `id` and `version` and does not depend on which format defines it, and one `(id, version)` is defined by exactly one of them.

**The binding.** A binding states its `id`, `version` and `profile`, a `scope` sentence saying what the name covers and what it does not claim, its publisher and source, the granularity it supports, every artefact that defines the profile, the validation steps in order, the finding severities that block, the identity rules below, its acceptance vectors and, optionally, which properties of the product document are public. Each artefact is listed with its role (`context`, `shapes`, `background` or `schema`), its byte length, its SHA-256 and its licence, and a context also with the URI documents name it by. The **binding digest** is the SHA-256 of the binding file's exact bytes, and the file holds no digest of itself. A binding is immutable: a changed binding is a new version. Binding format 1 supports the `item` granularity only.

**Registration.** A profile held by a binding is usable only once its binding is registered. A registry MUST refuse a binding whose digest is not on the list its operator trusts. It MUST refuse a second binding for an `(id, version)` already registered with a different digest, and registering the same bytes again changes nothing. It MUST hold every listed artefact to its recorded byte length and SHA-256 before the profile is used. How a deployment obtains the artefacts is its own.

**The payload.** A `payload_public` under a binding is one JSON object with exactly the members `profile`, `profile_version`, `profile_binding_sha256` and `product`, and optionally the `notice` of §5. `profile_binding_sha256` is the binding digest in lower-case hexadecimal, and `product` is the product document, unchanged, or its public properties where the binding states an access split. A payload in which any object carries one member name twice MUST be refused. A payload whose `profile_binding_sha256` is not the digest of the binding registered for its `profile` and `profile_version` MUST be refused.

**Validation.** A validator checks the envelope and the binding digest, then runs the steps the binding lists, in the binding's order. `json-schema` validates `product` against the binding's schema. `json-ld-expand` reads `product` as RDF using only the binding's contexts. `shacl` validates that RDF against the binding's shapes with its background data. `passport-identity` applies the identity rules below, and every binding lists it. A product document MUST name its contexts only by the URIs the binding lists: any other context, one written into the document included, is refused, and a validator MUST NOT fetch a context. A finding fails the check only when the binding lists its severity as blocking, and every finding is reported.

A binding MAY declare `validation.subjectClass` as an absolute class IRI when it lists the `shacl` step. A complete product MUST assert that class, or a subclass established by the binding’s shapes or background, on the unique subject named by `identity.subject.pointers`. The validator reads that subject’s `rdf:type` statements after expansion with the pinned contexts. Only the registered artefacts establish the subclass hierarchy. A missing or unrelated type on the complete subject fails. A public projection that cannot establish the required class reports the check as withheld. Introducing this field into a published binding requires a new profile version.

**A check that could not run is never a pass.** If any step fails, the result is `fail`. Otherwise, if any step could not run, the result is `unknown`. Only when every step ran and held is the result `pass`. A step could not run when the profile is not registered, when a validation engine is absent or lacks a capability the binding requires, when the engine did not finish in time, or when no passport identifier was supplied. A verifier reports the result under the `schema` check of [`verification.md`](verification.md) §4.

**Product-to-passport identity.** A product document can satisfy every rule of its own profile and still describe another product. The expected identity is the `passport_id` of the state being written or read, supplied by the writer or the verifier and never taken from the payload. The identifiers are read as GS1 Digital Links (§5).

1. Where no passport identifier is supplied, the result is `unknown`.
2. The product document's own identifier MUST be an uncompressed GS1 Digital Link with primary key 01 and a serial under 21, and its GTIN and serial MUST equal the passport's. A document that states two different identifiers fails.
3. The host is not compared.
4. A GTIN of 8, 12, 13 or 14 digits is compared at fourteen digits. A wrong check digit fails.
5. A serial read from a link is percent-decoded once and compared code point for code point, with no trimming, case folding or normalisation.
6. Every GTIN and serial the document states, at a member the binding names, MUST equal the subject's. For a JSON-LD binding, compare every value of the corresponding predicate asserted on the selected product subject. The binding's pinned contexts identify the predicate at its declared JSON Pointer, including property-scoped and type-scoped contexts along a nested path. A full IRI, compact name, allowed alias or second description of the same subject can express the same assertion. A conflicting assertion fails the comparison. An assertion whose value the verifier cannot interpret leaves the comparison unknown unless another assertion establishes a mismatch.
7. A passport or product identifier, at a member the binding names, MAY be coarser than the item. It MUST carry the same GTIN, and the same serial if it carries one.
8. A subject that is a model or a batch fails. A granularity the document declares MUST be `item`.
9. A related model or batch identifier is never compared as the subject.
10. A compressed link, another primary key or an identifier that is not a GS1 Digital Link gives `unknown`.
11. Nothing is rewritten: the comparison uses parsed values and the signed bytes stay as received.

**Public and restricted tiers.** A binding MAY carry an `access` member: a `policy` name, `tierSplit` `top-level-property`, `default` `restricted` and `public`, a list of property names. It divides the product document between `payload_public` and the restricted part held off chain ([`record-model.md`](record-model.md) §7). A binding without it has one tier, and the whole product document is public.

1. The split is by top-level property of the product document. Each top-level property is wholly public or wholly restricted, and nothing is split inside a nested object or a list.
2. A property is public only when `public` lists its name exactly as the document writes it. Every other property is restricted, one the binding does not name included.
3. The list is part of the binding, so the binding digest a payload declares also commits to which properties were public.
4. `public` MUST list every top-level property the identity rules read, and `@context` where the binding lists `json-ld-expand`. A registry MUST refuse a binding that does not. A binding SHOULD also list every property its rules select a node by, such as its type, under each name a document may write it.
5. A writer MUST validate the whole product document before it splits it, and MUST NOT issue from a document that fails or that could not be validated.
6. `product` in `payload_public` holds the public properties in the document's order. The restricted part holds every other property and repeats the product's own identifier, the join key. A document with no restricted property has no restricted part.

**Validation by view.** What a validator can decide depends on the parts it holds, and its result says which view it had.

- *Public view.* A reader with `payload_public` alone validates `product` as a projection of the whole document. A `product` that carries a property outside `public` MUST fail, because that property was disclosed, and nothing further is checked. A finding that reports only a missing value, on the product itself, along one property outside `public`, is a withheld check and not a failure. For `json-schema` that is a missing required top-level property, and for `shacl` a minimum count. Every other blocking finding fails. If any check was withheld, and nothing failed, the result is `unknown` and lists the withheld checks. The result is `pass` only when every rule could be evaluated and held.
- *Authorised view.* A reader with both parts checks the envelope and the binding digest, rejoins the parts and runs every step on the rejoined document, the identity rules included. Parts that do not rejoin fail, and the result names the refusal.

**Rejoining.** A rejoin MUST refuse, each under a code of its own: a part that is not one JSON object; a part without the join key; a restricted part whose join key is not the public part's; a property other than the join key that sits in both parts; a property outside `public` in the public part; a property in `public` in the restricted part. The rejoined document lists the public part's properties in their order, then the restricted part's, so the same parts always give the same JSON text. A rejoin serves validation and display. It is not what was signed.

**What the split does not establish.** A `pass` in the public view says that no rule the public payload could break is broken. It says nothing about the restricted properties, whose rules that reader never evaluated. Neither a `pass` in the authorised view nor a successful rejoin is evidence that a restricted part is the one a record commits to. That evidence is the comparison of the off-chain blob with `payload_owner_hash` ([`record-model.md`](record-model.md) §7), which a reader makes before relying on a restricted part, and nothing in this section replaces it. The split is by property name: a value a writer also states in a public property is public.

**Carrying a profile.** A profile held by a binding travels as a **profile bundle**: files inside a `dpp-evidence-package@1`, each listed in the package's inventory under the `schemas` category ([`portable-evidence.md`](portable-evidence.md) §2). A bundle is not another export format, and it adds no member to the package manifest. It occupies one folder of the package, `profiles` unless the exporter chooses another. For each profile it covers, a folder named `id@version` holds `binding.json`, which is the binding file in its exact bytes, each artefact the binding lists, at the path the binding gives, and each notice the binding lists. Beside those folders sits `profile-bundle.json`, the **descriptor**, conforming to `packages/dpp-profiles/schemas/profile-bundle-v1.schema.json`, and the text of each licence the exporter carries.

1. The descriptor lists every profile the bundle covers with the SHA-256 of its carried binding file and the notices carried for it, every licence a carried file is under with the path of its text where the text is carried, and every file that is named and not carried. A descriptor in which any object carries one member name twice MUST be refused.
2. A file whose publisher's terms do not let others pass it on MUST NOT be carried. It is listed as omitted, by the address its publisher publishes it at, its SHA-256 and its byte length, and a destination obtains it for itself. Every file GS1 publishes is treated so. An exporter MAY list in the same way a file no carried binding names and its deployment reads for other checks.
3. An exporter MUST carry every notice a binding lists, and MUST NOT export a binding's files when it cannot read a notice the binding lists.
4. A bundle covers profiles held by a binding. A profile defined by a manifest is published with the package that defines it and is not carried, and a binding's acceptance vectors are not carried.
5. The descriptor states three limits in fixed words, and a file that states any of them otherwise is not a descriptor. `profiles` is `bindings-only`, which is rule 4. `trust` is `destination-trusted-digests`: nothing in a bundle makes a binding trusted. `ownerCommitment` is `not-established`: validating a payload, or a disclosed part of one, under a carried profile is no statement about `payload_owner_hash`.

**Restoring from a bundle.** A deployment that restores a profile from a bundle registers the carried binding under the registration rules of this section, and under no others.

1. A destination MUST decide whether a carried binding is trusted from the list of binding digests its own operator configured. The descriptor, the manifest that lists the bundle and the signature on that manifest decide nothing: the signature says which exporter assembled the bytes, and an exporter is not a publisher of profiles.
2. A destination MUST refuse a carried binding whose digest is not on that list. Where it already holds the profile, or was told which digest to expect for it, it MUST refuse a carried binding with another digest as a substitution, without registering anything.
3. A destination MUST hold every carried artefact, and every file it supplies itself in place of an omitted one, to the byte length and SHA-256 the binding records, and MUST refuse the binding when any differs.
4. Each cause has a refusal of its own: no descriptor; a descriptor that cannot be read as one; a profile the bundle does not cover; a binding file the bundle lists and does not hold; a binding file that is not the one the descriptor names; a substituted binding; an untrusted binding; a trusted binding listed under another profile's name; an artefact the bundle lacks and does not list as omitted, which makes the bundle incomplete; an omitted file the destination did not supply; and an artefact that is not the file the binding records.
5. A profile that was refused is not registered, so a payload that declares it is `unknown` and never `pass`, as for any profile a registry does not hold.
6. A payload's `profile_binding_sha256` is compared with the restored binding's digest exactly as with any registered binding's, and a payload that declares another digest MUST be refused.

A restored profile validates as the same profile validates anywhere: by the steps, the views and the outcome rule of this section, with no context fetched. What the split does not establish, above, is unchanged by carrying a profile. A result from a restored profile, in either view, is not evidence that a restricted part is the one a record commits to.

**Updating a binding.** The files a binding lists are published by the profile's source, and the source may publish them again with changes. A changed file is never an edit to a binding. It is a candidate for the next version, and adopting it is a decision. An **update check** is the step before that decision: it compares the active version, as registered, with the candidate set of files the next version would list, and answers with a change report and a proposed binding.

1. A check MUST NOT register anything, and MUST NOT change the active binding, its artefacts or what a registry answers for them. A payload that declares the active version validates after a check exactly as it did before.
2. The report MUST list every artefact of either version as added, removed, changed or unchanged, with its role, licence, byte length and SHA-256 on each side that has it. A file the active version lists and the candidate leaves out is reported as removed and is never carried over.
3. For a JSON-LD context the report MUST list every term the candidate adds, removes or defines differently. A removed or redefined term MUST be marked as breaking, because a document that uses it is read differently under the proposed version, or not at all. A context that leaves the profile, that documents would name by another URI, or that no longer names another context the active version lists, is breaking in the same way: in the last case a document that names it alone loses the other context's terms. A context that could not be read MUST be reported as not compared, and never as unchanged.
4. For any other artefact a comparison by byte length and SHA-256 is enough, and the report MUST say that the artefact was compared in that way only.
5. Where the candidate is the active version's files, byte for byte, the check reports no change and proposes nothing.
6. Otherwise the proposal is a binding with the same `id`, a `version` above the active one and a binding digest of its own. Where no valid binding can be written from the candidate, the check proposes nothing and gives the reasons.
7. A proposal is registered only under the registration rules of this section. Its digest MUST be on the registry's trusted list, which the report never adds to, and it can never answer for the `(id, version)` it was derived from.
8. The report MUST state what the check did not do. A check that did not run the binding's acceptance vectors under the proposal says so, and the vectors are run before the proposal's digest is trusted.
9. The same active version and the same candidate MUST give the same report and the same proposed binding, in whatever order the candidate lists its files, so that two parties who run the check review one digest.

A deployment that adopts a proposed version keeps the earlier version registered beside it, because a state is read under the version it declares (§4).

## 8. Normative and implementation

What a conforming party reproduces: the manifest shape, version 2 included, and its immutability (§2), the field rules, the `needs-review` semantics, the three-valued evaluator and the shared shapes with the refusals their helpers make (§3), the versioning, the additive freezing discipline and the retirement rules (§4), the three granularities and the GS1 rules where selected (§5), generated rather than hand-kept consumers (§6), and, for a profile held by a binding, the binding shape and digest, the registration refusals, the payload envelope, the step order, the rule that a check that could not run is never a pass, the identity rules, and, where the binding states an access split, the split, the two views and the rejoin refusals, and, where a profile is carried or restored, the bundle's layout and descriptor, the rule that a file which may not be passed on is named and never carried, and the restore refusals, and, where a binding is checked against new files, the rules of the update check (§7). What is a build's own: which profiles it offers, how it renders a form, how it encrypts and where it stores the restricted tier, which resolver hosts its identifiers, which bindings it trusts, how it obtains their artefacts, which folder of a package it puts a bundle in, where it keeps the files it obtained for itself, which validation engines it runs, when it runs an update check, how it obtains the candidate files and how it writes a proposed binding's bytes.
