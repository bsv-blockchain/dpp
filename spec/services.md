# Service roles and verification boundaries

**Status: working draft, pre-1.0.** This document defines service roles around native records, secured attestations and independent overlays. It separates cryptographic verification from retrieval, identity, authority and current-status evidence.

## 1. No exclusive service operator

Native supplied-history verification uses transaction bytes and public block-header evidence. Credential verification additionally needs the selected proof, identity, status and authority material. Services may provide that material, but no named platform is a universal trust dependency. Missing evidence produces an explicit unavailable or indeterminate check; it does not establish validity or invalidity by itself.

A retained token tip and a transaction source can recover native predecessor transactions. They do not recover off-chain credential bodies or prove no later state exists. Readers MUST distinguish supplied-history validity, observed latest state and complete evidence availability.

An operator MAY run one or several roles. Independent operators MAY serve the same topics and immutable evidence. Two operators serve the same evidence for a lineage when the transactions and merkle paths they serve for it are byte-identical; the BEEF that carries them may differ in form, Atomic or not and with or without ancestors, by how each operator received the states. A comparison between operators, including any acceptance exercise that asks for identical evidence, compares those transactions and merkle paths, never the BEEF bytes. A client chooses the indexes it reads and MAY pin their hosts. How indexes find one another and synchronise is not part of this standard: the peer synchronisation of the reference index package is a feature of that package, documented with it, and SHIP/SLAP discovery and the federated operator profile are parked. No deployment is called independently replicated on the strength of synchronisation alone.

A publisher is not an operator. The keys that countersign admitted states and anchors are the index's publisher keys, which its capability document lists as the flat `publisherPolicy.publisherKeys` ([`../contracts/capabilities.schema.json`](../contracts/capabilities.schema.json)), with the anchoring services it accepts beside them, and a reader checks a state's publisher signature against the key its own policy names for that state ([`verification.md`](verification.md) §4, `publisherSignatures`). A signed history of those keys, with activation and retirement windows, rotation, handover and federation, is a feature of the reference index package, `dpp-publisher-policy@1` served at `GET /publisher-policy`, documented with that package and not part of this standard. The token spending key never moves by editing a list of publisher keys: it moves only through the custody or transfer mechanism of [`custody.md`](custody.md).

## 2. The overlay index

The current passport topic/service are tm_dpp and ls_dpp. The current attestation commitment topic/service are tm_attestation and ls_attestation. The legacy tm_uora_dpp and ls_uora_dpp interfaces serve historical anchor v3 separately. The legacy topics are read-only interfaces over the outputs already on chain; an index that serves them names the historical anchoring-service keys it carries and admits nothing else. [The overlay contract](../contracts/overlay.yaml) extends the BRC-22/BRC-24 interfaces with these admission and lookup rules.

The overlay contract has a core and extensions. The core is what the contract asks of every conforming index, each item at the level the must, should and may lists of `x-dpp-profile` give it: the topics and their admission rules, `POST /submit` with its `X-Admission` header, `POST /lookup` with the core query shapes, `POST /arc-ingest`, and the listing and documentation routes. Its version, `x-dpp-core-version`, changes only when the record versions the topics admit change or a must changes. Every other feature is an extension under `x-dpp-extensions`: the `X-Admission-Refusal` header, the capability document, the publisher policy route, registration, retraction, the GS1 key lookup, the evidence package, synchronisation, the health fields and the parked SHIP/SLAP discovery. Each carries its own version, which changes only with that extension, is optional, and marks the operations, headers and properties it adds. An extension fixes a wire shape and is no requirement of this standard: the behaviour behind the publisher policy route, registration and synchronisation is the reference index package's, documented with it, except for the registration request this section defines. The codes the `X-Admission-Refusal` extension lists are informative, the reference index's words, and a client reads any code as a refusal. An index may serve routes beyond the contract, and the reference package documents its own.

Passport admission checks the native state under its own record version and the selected custody policy. A version 2 state is admitted only when its lineage genesis can be traced, through the submitted bytes or the index's own admitted history, so that `lineage_genesis` is checked and never assumed; a state that spends a version 2 `RETIRE` is never admitted and the retired tip stays in place; a genesis that spends an admitted passport output is refused; and an index declaring `managed-custody@2`, or the superseded `managed-custody@1`, refuses a version 2 `TRANSFER` without its acceptance commitment. Record version 3, the token carrier, is parked outside the standard ([`../docs/reference/parked/token-carrier/`](../docs/reference/parked/token-carrier/README.md)). Generic anchor admission checks its exact script, framed metadata signature and anchoring-service key derivation. It does not validate a credential that is not present in the transaction. Returned BEEF enables independent transaction and inclusion verification; an index's response is not a global completeness or latest-state proof.

A state announced before it was sent ([`writing.md`](writing.md) §3) can be admitted and then refused by the network. The writer withdraws it through the retraction route of [the overlay contract](../contracts/overlay.yaml): the index forgets the output, tells its lookup services, makes the predecessor the tip again and records the reason; it refuses to withdraw an output it holds a merkle path for, one whose transaction its header source knows, or one a later state spends, because a history is never cut in the middle. A retraction is local to the index that receives it. An index that holds the state because it synchronised from another, as the reference index package can, keeps serving it as the lineage's tip until its own operator withdraws it through its own retraction route, under the same checks, so a state that index has since proven is never withdrawn by mistake. A writer or operator that knows which indexes pull from the ones it announced to SHOULD tell their operators, as it offers them proofs ([`writing.md`](writing.md) §7).

Current anchor lookup uses exact metadata selectors and an outpoint cursor. Callers retrieving history MUST continue through all pages. An operator may limit request size, but cannot silently describe a truncated result as complete.

An index MAY register a publisher key on the application's own request, so that an application reaches an open index from its documentation alone. The request is a `dpp-index-registration@1` object ([`index-registration.schema.json`](../contracts/index-registration.schema.json)): the index address the application targets, its publisher key, the network, the custody profile it writes under, a label and a request time, signed by the BRC-42 child of the publisher key for protocol `[1, 'dpp index registration v1']`, key identifier the index address and counterparty `anyone`, through the wallet's `createSignature`, so that the index verifies it from the request alone and a request signed for one index is refused by every other. An index that registers checks the signature before anything else, then that the request names its own address, its network and the custody profile its capability document declares, and that the request time lies within its clock window, and an accepted key appears in its capability document's publisher keys. Everything else is the index's own: whether a request is admitted at once or held, rate limits, refusal and revocation, and the write credentials it hands back. The reference index package documents its registration, which appends a version to its publisher policy chain and returns per-publisher write tokens.

Announcement failure changes discoverability, not transaction inclusion. Retry the same announcement rather than rebuilding an already submitted transaction. A mined transaction SHOULD be served with its Merkle proof. Pushed proofs MUST be checked against the transaction and the index's block-header source before storage. Unavailable headers defer proof acceptance.

## 3. The attestation registry

The registry stores immutable secured bytes, evaluates the selected representation and trust policy, and may anchor accepted evidence. Issuer, registry, anchoring service and overlay are separate roles. New submissions select the native claim format or a registered credential representation ([`exchange.md`](exchange.md) §1) explicitly. A registry MUST refuse a submission that selects neither, a historical UORA body among them, and store and anchor nothing; [the registry contract](../contracts/registry.yaml) answers it as `invalid`. There is no legacy intake for any submission to fall through to. A registry refuses a representation it does not implement as `unsupported`, naming `representation-unsupported`, and stores and anchors nothing; [the registry contract](../contracts/registry.yaml) refuses the parked `vsc-seal-json-v1` this way ([`vsc-profile.md`](vsc-profile.md)). A record stored under a representation the registry no longer accepts keeps its exact bytes and stays on every read route, its content reported as [`exchange.md`](exchange.md) §1 has a reader report a representation it does not implement.

[The registry contract](../contracts/registry.yaml) defines the minimum a registry serves: its capability document, validation, intake, the paged list of the records it holds, a record's anchor proof, a passport's chain and a passport's evidence package. A registry may offer more; the reference registry documents its own further routes. It is this standard's service contract, not a claim that a credential standard defines these paths. It defines no status list publication: a status list belongs to the issuer role, and a registry checks the lists issuers publish. Native records retain an explicit tokenRecordId for token-history assembly. A credential does not acquire a fabricated token state merely by being stored.

Store the complete original bytes, media type, representation, digest, verified metadata and scoped verification report. Corrections and projections create new records and retain their source relationships. Unauthenticated status lists and self-asserted authority do not satisfy active credential validation.

A registry records the relations between claims independently of token spending: `supersedes`, `revokes`, `suspends`, `expires` and `disputes` are relations between attestations, and none is implied by a passport state changing hands. A claim can be historically authentic and currently superseded. An observation about a product does not automatically compete with every other observation about that product: competing custody claims, input-consuming transformations and independent assessments have distinct conflict rules, and the historical authority precedence applies only between claims under one comparable named trust framework. Otherwise the registry returns an unresolved conflict rather than a winner. Antecedents are resolved by their expected identifier and verified content under bounded traversal, with a shared ancestor in a diamond valid and a true cycle refused; a missing or mismatched ancestor stays unresolved with its reason. An external lifecycle event records its identifier, product references, event time, claimant, evidence, quantities and units, facility references where relevant, predecessor and related claims and its mapping profile and version; it binds to a passport state where one exists and may otherwise reference the stable product identifier without any token spend.

Historical UORA representations, native and SD-JWT, are read and never accepted anew. A record stored under one keeps its original identifier and reported assurance, stays readable as `legacy-uora-json`, and never acquires a current representation's conformance. It retains no secured bytes, only the canonical bytes its digest commits to: under [the registry contract](../contracts/registry.yaml) the record list names it, the proof and chain routes serve those canonical bytes, and the evidence package names it under what the registry could not produce. A registry that holds such records names `legacy-uora-json` under `unsupported` in the registry contract's capability document.

## 4. Verification surfaces

Report native signature, token linkage, anchor attribution, representation digest, credential proof, issuer identity, authority, credential status, event time, custody graph, corrections and inclusion separately where applicable. An unavailable required check prevents dependent acceptance. A native proof result cannot be reused as a credential proof result. [The verification contract](verification.md) fixes the report every surface produces: sixteen named checks with four answers each, an independently expected subject, and an observation of the latest state that is never a proof.

An aggregate operation outcome MAY decide intake only when its required check set and policy are explicit. User-facing output MUST retain the per-check findings and must not label an anchor-only result as a verified physical claim. A derived disclosure presentation is verified with its own suite and challenge binding; matching visible fields does not prove equality with anchored full credential bytes.

## 5. Identifier resolution

[Identity](identity.md) separates physical-object DIDs, actor DIDs, credential ids, token keys and application accounts. Resolve only under declared method and security policies. A nomination inside untrusted data is not automatically an accepted trust anchor. Offline verification can use retained authenticated resolution evidence and must report its time/scope; it cannot infer current control or revocation state from historical evidence alone.

## 6. Operator conformance

Operators declare implemented roles, formats, versions and limits. The operator profiles an index names in its capability document and evidence packages, and the `scope.operatorProfile` of a publisher policy, are the reference index package's labels for how it is administered and synchronised, documented with it; `federated-operators@1` is parked. Replay of an admitted outpoint is idempotent. Reorganisation eviction and recovery use the same exact evidence rules. Deployment policy may restrict who submits or which anchoring services are accepted, but cannot relax signature or byte rules while advertising the same conformance profile. An index MAY require write credentials on its write routes; how it issues and binds them is its own, and the reference index package documents its per-publisher tokens.

Operational availability, independently replicated overlays, credential-format compatibility and industry applicability are separate claims. A profile that records local resolutions of upstream draft ambiguities cannot be described as upstream certification.
