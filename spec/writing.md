# Writing a state: the writer's lifecycle

**Status: working draft, pre-1.0.** This document defines what the party that writes a state owes the record: the order in which a state is checked, announced and sent, the rule that keeps two writers from forking a passport, and the duties to prove and to keep what was written. The record model defines what a state is and what a verifier checks; the services document defines what runs around the records; this document stands between the two, because the property they protect, that a stranger verifies from bytes and headers alone, is only as good as the bytes and proofs someone kept. The rules apply to both rails: a passport state and an anchor are written the same way.

## 1. The writer

The writer is the party whose BRC-100 wallet makes the transaction. On the passport rail that is whoever holds the locking key of the tip ([`custody.md`](custody.md) §3): an issuer at genesis, an operator under split or operator custody, the owner under possession. On the anchor rail it is the attestation registry ([`rules.md`](rules.md) §3). The rules below are duties of the writer, stated as outcomes a stranger could check after the fact rather than as steps a particular product performs, and a wallet discharges several of them on the writer's behalf (§10). Where a rule names an interface, it names the ecosystem's: the BRC-100 wallet interface for making and sending a transaction, BRC-22 for announcing to an index, and the broadcast and proof interfaces the stack documents. It names no service, because a duty that could only be met with one operator's service would make that operator load-bearing, which [`services.md`](services.md) §1 forbids.

## 2. Verify before sending

A writer MUST run the verifier's own checks on a candidate state before it is broadcast or announced: decode the state from the locking script it built, check the chain invariants against the tip it spends ([`record-model.md`](record-model.md) §6), verify both signatures (§5), and evaluate the owner-signed transfer where the profile selects it ([`custody.md`](custody.md) §4). A genesis is checked alone against the rules for `ACTIVATE`. The reason is that the chain cannot be edited: an invalid state, once mined, is a permanent output that every reader refuses and that the next writer must still spend to continue the passport, so the only moment at which a mistake costs nothing is before the bytes leave the wallet. The recipe is the reader's: reconstruct the chain from the tip's BEEF, append the candidate, and run the whole verification with the header check disabled, since nothing is mined yet. A writer that trusts its own encoder is exactly the writer this rule exists for.

## 3. Announce before sending

Where an index is named for the deployment, a writer SHOULD build the transaction unsent, announce it, and send it only once the index admits it. Admission applies the checks of §2 plus the operator's policy, so a refusal reaches the writer while the state is still a draft that can be discarded at no cost; sent first, the same refusal arrives about an output that already exists. The BRC-100 interface supports the order directly: an action created unsent is complete and signed, and a later action sends it. Two qualifications keep this from making the index load-bearing. An unreachable index is not a refusal, only an answer is; a writer that cannot reach its index sends anyway and announces later (§6). And an index MAY broadcast what it admits, as the ecosystem's overlay engine does when it is given a broadcaster; a second broadcast of the same bytes is harmless, because the network's answer to a transaction it already holds is that transaction's status.

## 4. One writer per passport

The tip is spent once. A writer MUST serialise its writes per passport, record the network's answer for every state it sends, and spend a tip a second time only after it has learnt the fate of the first spend. The fates are three, and they are the standard's whole vocabulary for a sent transaction: accepted or seen by the network, and the state exists and is `pending` until mined; rejected, and the state never existed and the tip is unspent, so the writer may build again; competing with another spend of the same tip, and the writer waits for mining to learn which one exists. Two concurrent writers of one passport double-spend its tip, the network keeps one, and everything built on the other, states, announcements, attestations, is void.

A state handed to a queue is not yet written. A writer MUST NOT report a state as written, to a user, to a registry or to its own store, before the network or the wallet's broadcaster has answered for it. A wallet that queues broadcasts for a background process answers "signed and handed off", which is a statement about the wallet and not about the network; the reference application reported success on that answer and was, for about ten minutes at a time, describing a state the network had never seen. The BRC-100 interface lets a writer choose the synchronous answer, and a writer that does not choose it MUST wait for the queue's result before speaking.

## 5. Broadcast

The writer's wallet broadcasts: sending is the wallet's `createAction`, and how it reaches miners is the wallet's business, which is what lets an owner's own wallet write a transfer under possession without any arrangement with a deployment. A deployment that runs its own wallet infrastructure SHOULD configure it to broadcast through an ARC-compatible endpoint that delivers merkle proofs by callback, to more than one endpoint so that no single broadcaster's outage stops writing, to read fee policy from the endpoint rather than to hard-code it, and to run the wallet's monitoring process, because a wallet that is not watching learns of nothing, neither mining nor rejection. Which endpoints are a deployment's own choice, and the informative material beside this standard names the ones the ecosystem operates.

The status vocabulary the standard needs is §4's. A broadcaster's finer distinctions, how many nodes have seen a transaction or how deep its block is, are the broadcaster's opinion and not a verifier's finding, and the standard names no confirmation depth: a state is proven when its merkle path validates against block headers ([`record-model.md`](record-model.md) §8), and `pending` before, and a reorganisation that refutes a proof returns it to `pending` (§9). A deployment may show its users whatever a broadcaster reports; it may not make the record's truth depend on it.

## 6. Announce

Announcing to an index is discoverability, never existence ([`services.md`](services.md) §2). A conforming writer MUST NOT fail a record over a failed announcement, and MUST retry a failed announcement rather than spend again: a record that exists on chain and is missing from an index is repaired by announcing it, and a writer that instead rebuilt the state spent a second output on a passport that already had one, which is how the reference application produced orphan records before the fault was found. Announcing is idempotent by construction, since an index treats a held output as a no-op ([`services.md`](services.md) §6), so retrying costs nothing. A non-genesis state is announced with its predecessor's bytes in the same BEEF, because an index admits a state against the tip it spends; a backfill therefore runs in chain order, genesis first. A writer announces to every index the profile names, or to the host it has pinned, and a public writer SHOULD find its indexes through the overlay discovery protocols rather than through configuration alone.

## 7. The proof

For every state it writes, the writer MUST obtain the merkle path once the state is mined, attach it to the BEEF it holds for the state, and keep it (§8). Where the proof comes from is a build's choice: the callback the writer's broadcaster delivers, that broadcaster's status query, a proof service, or the writer's own node. What is not a choice is whether it arrives: until it does, the state reads `pending` to every verifier, and a passport whose proofs nobody obtained is not yet what §1 of the record model promises.

The writer SHOULD offer the proof to every index it announced the state to, through the index's proof-ingestion route, unless the index's own broadcaster delivered it. The reason is structural. An index stores a state's bytes at admission, which under §3 happens before mining, so the BEEF it holds carries no proof; and re-announcing the state later does nothing, because admission of a held output is a no-op and the stored bytes stay as they were. The proof therefore has to be pushed, and the writer is the party that has it. An index that obtains proofs for itself is conforming and welcome ([`services.md`](services.md) §2), and a writer cannot rely on it. What travels is the proof alone, never a second copy of the state: the merkle path in the BRC-74 format, the transaction identifier it proves, and the block height, which is the shape a broadcaster's own callback carries, so an index accepts the same body from either.

## 8. Retain

A writer MUST retain, for every state it writes and for the life of the passport, the raw transaction, the BEEF it was sent as, and the proof once obtained. Neither the broadcaster nor the index is the store of record: a broadcaster's status is per instance and ages out, and an index is a courtesy that any operator may run and any operator may stop ([`services.md`](services.md) §1). The property the standard protects is that a stranger verifies from bytes and headers; if the writer does not hold the bytes, that stranger depends on whoever does, and the record is true and gone. A wallet retains what it wrote as part of being a wallet, and under possession the owner's wallet is this store; a deployment that writes through its own infrastructure holds the same material in its own store, beside its account records, as the primary copy.

## 9. Reorganisations

A block can be orphaned, and a proof against it is then refuted by the header source, which returns the state to `pending` until a proof against the surviving chain replaces it ([`record-model.md`](record-model.md) §8). The writer obtains the new proof as §7 describes, and nothing in the record changes: the state's bytes, its position in the chain and its signatures are what they were, because a reorganisation moves transactions between blocks and does not rewrite them. A writer that waits a block before seeking a proof avoids most of this work, and a writer that seeks it at once must be prepared to seek it again.

## 10. Personal wallets

Under possession ([`custody.md`](custody.md) §5) the owner's BRC-100 wallet performs §5, obtains and keeps the proof of §7 and retains the bytes of §8, because pursuing broadcast and proof and holding what it signed is what a wallet is. The owner's application, the software that assembles the state and talks to the index, keeps §2, §3, §4 and §6, and offers the proof under §7 once the wallet has it, which it reads from the wallet by the interface's own means. Under split and operator custody the operator's wallet infrastructure plays the wallet's part and the operator's service the application's. The division is the same in every arrangement, which is why this document can state one set of duties without preferring one.

## 11. Normative and implementation

What a conforming writer reproduces: the check of §2 before any send or announcement; the order of §3 where it claims to follow it; the tip rule and the not-yet-written rule of §4; the announcement rules of §6, that a failed announcement never fails a record and is retried, never rebuilt; the proof duty of §7, obtained, attached and offered; and the retention of §8. What is a build's own: which wallet, which broadcasters and how many, which indexes, fee policy, where the retained bytes live, and how long a writer waits for an answer before it reports one. Conformance of a writer is self-reported against this list, one sentence per rule, as [`../GOVERNANCE.md`](../GOVERNANCE.md) describes, because no byte vector can certify behaviour.
