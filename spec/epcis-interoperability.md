# EPCIS interoperability: source exchange and explicit mapping

**Status: working draft, pre-1.0.** This document defines how a passport's evidence services take in, retain, query, map and export GS1 EPCIS 2.0.1 event data: the `epcis-json@1` source exchange profile and the `epcis-vsc@1` mapping profile, both catalogued in `packages/dpp-profiles/manifests/interoperability/` under `schemas/interoperability-profile.schema.json`. It changes nothing about the native record, the native claim, the generic anchor or the VSC profile; a mapped credential still passes [`vsc-profile.md`](vsc-profile.md) unchanged, and an import is a data operation that never touches [`record-model-v2.md`](record-model-v2.md). The reference implementation is `packages/vsc` (`epcis-source.ts`, `epcis.ts`) for everything shared, and the application service for everything durable.

## 1. Supported inputs and limits

A source is a UTF-8 JSON or JSON-LD document of media type `application/json` or `application/ld+json` whose root is an `EPCISDocument` or an `EPCISQueryDocument`, read against the pinned EPCIS 2.0.1 JSON Schema and JSON-LD context (`packages/vsc/artifacts/epcis/`, digests in the profile manifest and in `EPCIS_ARTEFACTS`). The five event types `ObjectEvent`, `AggregationEvent`, `TransformationEvent`, `TransactionEvent` and `AssociationEvent` are recognised; an extension event type is retained with its pointer and identity and not interpreted. A bare event is accepted as a source only when the caller supplies the envelope type and context declarations it travelled with.

Before anything is retained, the transport is inspected and refused by name for: an unsupported media type; a document over the byte limit; malformed UTF-8; malformed JSON; a member name repeated within one object; a container nested deeper than the depth limit; a number a double cannot carry exactly (an overflow to infinity, or a literal whose decimal digits are lost, such as `9007199254740993`); more events than the per-document limit; a root that is not an object. A refusal produces no retained record and no side effect. A document that parses safely and then fails the EPCIS schema, an envelope check or an identifier rule is retained with its findings; it is evidence that was received, and it is publishable on no basis.

Nothing is stripped, coerced, reordered, compacted or rewritten to make a source pass: explanatory members, numeric strings, vocabulary spellings and identifiers stay exactly as received. Members the schema does not name for the envelope or the event type are listed as preserved extensions. A separately selected adapter MAY produce a derived candidate document with a change log, its own digest and a fresh validation report; the original stays intact and is never described as conformant because a transformed copy passes.

The initial default limits, disclosed in the profile manifest and in every result, are 2 MiB per document or query page, 100 events per document or page, JSON depth 64, 16 context documents totalling at most 1 MiB, a 10 second fetch timeout, and a pull run of at most 10 pages, 20 MiB and 60 seconds. An operator MAY lower a limit or explicitly configure a bounded higher one. Exceeding a limit is never reported as complete history.

## 2. The retained source

An accepted import persists the exact received bytes before it is acknowledged, and its durable record conforms to [`../contracts/epcis-import.schema.json`](../contracts/epcis-import.schema.json): a stable `importId`; the caller's `requestId` bound to the digest of its request; the configured `sourceId`, which names a configured origin and never an account type; `receivedAt`, `mediaType`, `byteLength`, `sha256` and `bytesRef` for the exact representation; a `sourceLocation` that is provenance without credentials; the `contextRefs` exactly as declared with their pinned digests or the statement that a context is unpinned; the `profileRefs` and `policyId` the import was interpreted under; per-event results; and the pull `progress`. Export returns the retained bytes under the received media type, or nothing; a newly generated event document is a projection with its own identity and is never presented as the original envelope.

Every event has a scoped identity. An event that carries an `eventID` is identified by the configured source identity and that `eventID`. An event without one is valid where EPCIS permits it and receives a local ingestion identity, `urn:bsv:dpp:epcis:local-event:sha256:<hex>`, derived from the source digest and the event's JSON pointer; it is labelled local and never written into the source.

Every event has a body digest: RFC 8785 canonical JSON over the event with its repository `recordTime` and its `errorDeclaration` removed, beside the sorted digests of the pinned contexts it was read under, hashed with SHA-256. Two formattings of one event digest the same; two JSON-LD spellings of one meaning do not, and equivalence across arbitrary terms or sources is not promised. The comparison bytes are separate from the retained original, and the digest is taken over parsed values, which is why the transport check refuses a number literal the parse would change.

Arrival under an identity already held is classified, never merged: an equal body with an equal `recordTime` and error declaration is a duplicate; an equal body with a changed `recordTime` or error declaration is a further observation of the same event and no permission to overwrite it; a different body is a conflict that stays visible, both bodies retained, until it is explicitly resolved by name. An identical retry of a request under the same `requestId` resumes or returns the same import; the same `requestId` with different bytes is a conflict.

## 3. The pull connector

The application service provides a file import and a configured HTTPS pull client. The pull client consumes the standard events query of the pinned REST binding (`GET /events`, `openapi.json` digest `3d33792c520d7a7a1d080382d956730bb07021c7dd1cc17229fce27b784d66fc`), initially with product selection through `MATCH_anyEPC`, event type selection through `eventType`, time bounds through `GE_eventTime`, `LT_eventTime` and `GE_recordTime`, explicit refresh through `EQ_eventID`, and paging through `perPage`, `nextPageToken` and the `Link` header with `rel="next"`. `GS1-EPCIS-Version` and `GS1-CBV-Version` name the wire versions; document release numbers are never substituted for them. No provider-specific parameter is the standard query interface.

Credentials and permitted origins are server configuration. Every redirect and every pagination target is revalidated against the permitted origins; a credential is never forwarded to another origin; private-network targets and DNS rebinding are refused except under an explicit local-test configuration; the same bounded loader policy governs contexts, DID documents and status resources. A page is checkpointed only after its imports and their results are durable. After an interruption or an expired page token, a bounded replay with deduplication resumes the same configured query.

Each pull reports one of eight outcomes and they are never mistaken for one another: `source-link-missing` when discovery found no EPCIS link; `source-authentication-required` when the source demanded credentials; `source-forbidden` when it refused this caller; `source-unavailable` when it did not answer or answered an error; `unexpected-media-type` when it answered something that is not EPCIS, which is what an HTML sign-in page with status 200 is; `invalid-source` when the bytes were refused before retention; `partial-history` when the bounded query ended before the source did; and `ok` when the bounded query completed. A completed query that matched nothing is `ok` with an empty event list. Every result declares the selected subject, the query, the source and its completeness limits; a bound on record time cannot discover every retrospective error declaration, an exact-subject query does not retrieve the ancestral transformations of its inputs, and retrieving further identifiers requires explicit scope. Subscriptions, guaranteed synchronisation and a repository crawler are outside this profile.

## 4. The service and its HTTP surface

The service API provides `importEpcis`, `getEpcisImport`, `pullEpcis`, `publishMappedEvent` and `exportEpcisSource`, with injectable store, source client, clock, authorisation and credential publisher. Import and pull default to validation and retention; `publishMappedEvent` is a separately authorised action a scoped automation policy MAY invoke; no method accepts a token operation.

The application exposes thin authenticated routes under `/api/interoperability/epcis`: `POST /imports`, `GET /imports/{id}`, `POST /pulls`, `POST /imports/{id}/events/{eventRef}/publish` and `GET /imports/{id}/source`. The import body carries the exact source bytes as a UTF-8 string with the declared media type and the configured source identity; the 2 MiB limit applies to the decoded bytes and the request envelope is capped at 6 MiB. `eventRef` is an opaque URL-safe reference to a retained event pointer. Permission comes from the server adapter, never from a role in the body, and a caller-supplied source URL confers nothing. Source download returns the original media type and bytes.

Status codes are fixed: 400 for a malformed request; 401 and 403 for authentication and authorisation; 404 for a record that is unavailable or may not be disclosed; 409 for an idempotency or content conflict; 413 for a size limit; 415 for an unsupported transport format; 201 with the durable result and per-event findings for a completed new import, even when no event is publishable; 200 with the existing result for an identical completed retry; 202 with an operation reference for asynchronous work; 422 for an explicit publication request that fails required validation; a retryable operational result for an unavailable dependency. Every error carries a stable code and the affected event pointers.

Import states are `received`, `evaluated`, `publication-pending`, `published` and `blocked`, with per-event outcomes retained. Operational state never substitutes for the verification report of [`verification.md`](verification.md).

## 5. Mapping into the VSC profile

`mapEpcisEvent` and its round-trip extension `urn:bsv:vsc:vocab:epcis-roundtrip:0.1.0` are unchanged. `mapEpcisEventWithReport` wraps them and returns one of four outcomes with its reasons: `lossless` when the event carries nothing the profile cannot express, so the SEAL's event vector and the round-trip extension together carry every source member; `transformed` when the event carries semantics the event vector does not, each named after an `epcis-vsc@1` mapping limit (parties, business transactions, sensor elements, quantities, persistent dispositions, master data, certification references, error declarations, transformation identifiers, event-level contexts, extension members, multi-product events, a caller-decided transformation action); `unsupported` when the profile cannot express the event or a decision is missing (an extension event type, a `TransformationEvent` without an explicit action decision, an action outside `ADD`, `OBSERVE` and `DELETE`, a disposition the custody model does not name, an identifier scheme the profile does not carry); and `insufficient-data` when the source lacks an input the mapping never fabricates (`eventTime`, `eventTimeZoneOffset`, `bizStep`, `disposition`, a recorded time, a product identifier). Retention alone is never a lossless claim.

A mapped SEAL carries, beside the round-trip event, the signed source reference `urn:bsv:dpp:epcis-source:1`: the digest and media type of the exact source bytes, the event's pointer, its `eventID` when present, the sorted digests of the contexts it was read under, and the mapping profile. The reference lets a verifier fetch the retained bytes, locate the event and recompute its body digest; it asserts nothing about the source's truth.

The SEAL's actor is the signing issuer. A party the event names in its source list, destination list or business location is retained in the extension and never projected into `who`; an issuer that attests to receiving another party's report is not thereby attesting that it performed the physical event. Issuance is a separate, separately authorised step that requires the actual issuer and assertion key, role, jurisdiction, status entry and custody evidence, and the complete SEAL is then evaluated under the VSC profile including its Q-state transitions, subject continuity and correction rules. Those rules are not changed to admit a maintenance observation or a multi-product event; an event that is valid EPCIS and unpublishable as this profile stays access-controlled evidence with an explicit outcome, is not submitted to the secured-credential endpoint, and is never relabelled as a signed claim.

## 6. Error declarations and corrections

An `errorDeclaration` is retained with its declaration time, reason and corrective event references and reported per event. It is resolved only when every corrective event it names is held under the same source; otherwise it is unresolved and stays so. An EPCIS error declaration is not a VSC `correctionOf` and grants no correction authority: a VSC correction requires the existing issuer or a verified scoped delegate, the correction chain and the reason evidence of [`vsc-profile.md`](vsc-profile.md) section 5. Competing corrections remain conflicts; earlier signed bytes are retained.

## 7. Tokens, publication and recovery

No import, pull, mapping or export invokes `ISSUE`, `UPDATE`, `TRANSFER` or `RETIRE`. Shipping, receiving, owning-party and possessing-party fields establish neither token authority nor recipient acceptance. A later business workflow MAY cite retained source evidence when it calls the passport service; that service independently validates the current tip, the actor's authority and the recipient's acceptance. Retiring a token does not erase the event store and does not prevent a separately authorised later attestation.

A publication persists the immutable issued credential and its identifier before submitting it for anchoring, and records the durable operation it runs under. A retry after an uncertain answer queries the existing credential and anchor result through the existing journal and recovery interfaces; it never issues a fresh credential or spends again blindly.

## 8. Normative and implementation

What a conforming party reproduces: the supported inputs, the refusals before retention, the retention-with-findings rule and the disclosed limits (section 1); the retained source contract, the scoped identities, the body digest and the arrival classification (section 2); the standard query consumption, the loader policy and the eight outcomes (section 3); the service and route contract with its status codes (section 4); the four mapping outcomes, the source reference and the attribution rule (section 5); the treatment of error declarations (section 6); and the separation from token operations and the publication recovery rule (section 7). What is a build's own: where bytes are retained, which store holds the import record, how `eventRef` is encoded, which automation policy may request publication, and which limits an operator lowers or raises within the profile's bounds.
