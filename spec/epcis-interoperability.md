# EPCIS interoperability: source exchange and explicit mapping

**Status: working draft, pre-1.0.** This document defines how a passport's evidence services take in, retain, query, map and export GS1 EPCIS 2.0.1 event data: the `epcis-json@1` source exchange profile and the `epcis-vsc@1` and `epcis-vsc@2` mapping profiles, all catalogued in `packages/dpp-profiles/manifests/interoperability/` under `schemas/interoperability-profile.schema.json`. It changes nothing about the native record, the native claim, the generic anchor or the VSC profile; a mapped credential still passes [`vsc-profile.md`](vsc-profile.md) unchanged, and an import is a data operation that never touches [`record-model-v2.md`](record-model-v2.md). The reference implementation is `packages/dpp-credentials`: `epcis-source.ts` for the shared source exchange, and `epcis-exchange.ts` for file import, the query pull of section 3, retention, arrival, conflict decisions, export and the operational recovery of section 8, over storage and a transport the application supplies. The parked mappings' implementation, `epcis.ts`, is no longer in the package.

**The mapping profiles are parked.** `epcis-vsc@1` and `epcis-vsc@2` map into the parked [VSC compatibility profile](vsc-profile.md) and are parked with it: optional compatibility profiles that no release selection requires and that the programme does not currently develop. That covers section 5, the mapping rules of section 6, and the publication of a mapped event in section 7. Their reference implementation is no longer part of `@bsv/dpp-credentials`: from version 0.2.0-beta.6 the package exports neither mapping, and the code and its tests stay in the repository history at commit `8c82c5e6ca31cd991e701d1051047153c7395eae`; the published 0.2.0-beta.5 still carries `epcis-vsc@1`. Their vectors stay as published, and their manifests change only in their status, which reads `parked`. An implementer need not support them; an implementation that does not records each event's mapping outcome as `not-attempted` in its import record ([`../contracts/epcis-import.schema.json`](../contracts/epcis-import.schema.json)) and offers no publication of a mapped event. The source exchange profile, `epcis-json@1`, is not parked: its inputs and limits, retained source, body digest, arrival classification, pull connector, import and export, and the retention of error declarations stand as written.

The exchange profile [`epcis-event-profile.md`](epcis-event-profile.md) (`epcis-event-vc@1`) describes an EPCIS event signed and anchored by its own party without a mapping: the event itself is the credential subject, keyed by its CBV 2.0 Event Hash ID and signed with the party's own key. It is parked while its representation is reconsidered, and no release requires it. That profile changes nothing this document says about intake, retention or the parked mappings, and an imported event retained under `epcis-json@1` is signable under it by the party that observed it, not by the importer.

## 1. Supported inputs and limits

A source is a UTF-8 JSON or JSON-LD document of media type `application/json` or `application/ld+json` whose root is an `EPCISDocument` or an `EPCISQueryDocument`, read against the pinned EPCIS 2.0.1 JSON Schema and JSON-LD context (digests in the profile manifest and in `EPCIS_ARTEFACTS`; GS1 publishes the files under its own terms, so the reference package pins them and obtains them from GS1 rather than carrying them). The five event types `ObjectEvent`, `AggregationEvent`, `TransformationEvent`, `TransactionEvent` and `AssociationEvent` are recognised; an extension event type is retained with its pointer and identity and not interpreted. A bare event is accepted as a source only when the caller supplies the envelope type and context declarations it travelled with.

Before anything is retained, the transport is inspected and refused by name for: an unsupported media type; a document over the byte limit; malformed UTF-8; malformed JSON; a member name repeated within one object; a container nested deeper than the depth limit; a number a double cannot carry exactly (an overflow to infinity, or a literal whose decimal digits are lost, such as `9007199254740993`); more events than the per-document limit; a root that is not an object; more distinct context declarations than the context document limit, or inline contexts whose canonical forms total more than the context byte limit; a string that has no canonical form to digest, which is one with an unpaired surrogate. A refusal produces no retained record and no side effect. An importer that does not hold the pinned schema refuses the import the same way: a source is never retained unvalidated and never passed without the schema. A document that parses safely and then fails the EPCIS schema, an envelope check or an identifier rule is retained with its findings; it is evidence that was received, and it is publishable on no basis.

Nothing is stripped, coerced, reordered, compacted or rewritten to make a source pass: explanatory members, numeric strings, vocabulary spellings and identifiers stay exactly as received. Members the schema does not name for the envelope or the event type are listed as preserved extensions. A separately selected adapter MAY produce a derived candidate document with a change log, its own digest and a fresh validation report; the original stays intact and is never described as conformant because a transformed copy passes.

The initial default limits, disclosed in the profile manifest and in every result, are 2 MiB per document or query page, 100 events per document or page, JSON depth 64, 16 context documents totalling at most 1 MiB, a 10 second fetch timeout, and a pull run of at most 10 pages, 20 MiB and 60 seconds. An operator MAY lower a limit or explicitly configure a bounded higher one. Exceeding a limit is never reported as complete history.

## 2. The retained source

An accepted import persists the exact received bytes and a recoverable record before it is acknowledged, and its durable record conforms to [`../contracts/epcis-import.schema.json`](../contracts/epcis-import.schema.json), version 2: a stable `importId`; the caller's `requestId` bound to `requestDigest`, the digest of its request, with the `idempotency` scope within which the `requestId` is unique and the rule by which a repeat is compared; the configured `sourceId`, which names a configured origin and never an account type; `receivedAt`, `mediaType`, `byteLength`, `sha256` and `bytesRef` for the exact representation; a `sourceLocation` that is provenance without credentials; the `contextRefs` exactly as declared with their pinned digests or the statement that a context is unpinned; the `profileRefs` and `policyId` the import was interpreted under; per-event results; the pull `progress`; its `documentValidity`, `valid` only when the envelope is recognised, the pinned schema accepted the document and no envelope, context or identifier check failed; and its `state`, one of `received`, `evaluated`, `publication-pending`, `published` and `blocked`, which is operational and never substitutes for the verification report of [`verification.md`](verification.md). Neither says who made the document or that an event in it happened: a valid document is not a signed one. The request digest of a file import, and of one page of a query, is SHA-256 over the RFC 8785 form of an object with exactly the members `byteLength`, `mediaType`, `sha256` and `sourceId`; receipt time, provenance and policy are not part of it. A record stored under version 1, which did not require `requestDigest`, validates under [`../contracts/epcis-import-v1.schema.json`](../contracts/epcis-import-v1.schema.json). The other durable records of an exchange, which are each observation of an event, each conflict decision, each index entry, the journal of unfinished work, the state of each pull, each page a pull acknowledged, and the record of each recovery snapshot restored into the store with where its originals were placed, conform to [`../contracts/epcis-exchange-records.schema.json`](../contracts/epcis-exchange-records.schema.json), each with its own type and version. Export returns the retained bytes under the received media type, or nothing; a newly generated event document is a projection with its own identity and is never presented as the original envelope.

Every event has a scoped identity. An event that carries an `eventID` is identified by the configured source identity and that `eventID`. An event without one is valid where EPCIS permits it and receives a local ingestion identity, `urn:bsv:dpp:epcis:local-event:sha256:<hex>`, derived from the source digest and the event's JSON pointer; it is labelled local and never written into the source. The two kinds of identity are compared apart: an `eventID` written in the form of a local identity is still an `eventID` and never meets the event that identity was assigned to. Neither is a CBV Event Hash ID, and an import computes none.

Every event has a body digest: RFC 8785 canonical JSON over the event with its repository `recordTime` and its `errorDeclaration` removed, beside the sorted digests of the pinned contexts it was read under, hashed with SHA-256. Two formattings of one event digest the same; two JSON-LD spellings of one meaning do not, and equivalence across arbitrary terms or sources is not promised. The comparison bytes are separate from the retained original, and the digest is taken over parsed values, which is why the transport check refuses a number literal the parse would change.

Arrival under an identity already held is classified, never merged: an equal body with an equal `recordTime` and error declaration is a duplicate; an equal body with a changed `recordTime` or error declaration is a further observation of the same event and no permission to overwrite it; a different body is a conflict that stays visible, both bodies retained, until it is explicitly resolved by name. Where the identity already holds more than one observation the arriving event is compared with each: it is a duplicate when any held observation has its body, `recordTime` and error declaration, otherwise a further observation when any has its body, and a conflict only when none has. A duplicate adds no observation. A conflict is resolved by a recorded decision that states what was decided, its disposition and its time and names every competing observation; the decision changes and removes none of them, is appended and never edited, and covers the bodies held when it was made, so a body that arrives later reopens the conflict. An identical retry of a request under the same `requestId` resumes or returns the same import and creates no second record; the same `requestId` with different bytes is a conflict, and the earlier import stands.

## 3. The pull connector

The application service provides a file import and a configured HTTPS pull client. The pull client consumes the standard events query of the pinned REST binding (`GET /events`, `openapi.json` digest `3d33792c520d7a7a1d080382d956730bb07021c7dd1cc17229fce27b784d66fc`), initially with product selection through `MATCH_anyEPC`, event type selection through `eventType`, time bounds through `GE_eventTime`, `LT_eventTime` and `GE_recordTime`, explicit refresh through `EQ_eventID`, and paging through `perPage`, `nextPageToken` and the `Link` header with `rel="next"`. `GS1-EPCIS-Version` and `GS1-CBV-Version` name the versions a request is made under: by default the pinned EPCIS version, 2.0.1, and the pinned CBV version, 2.0.0, each written with three parts as the interface description gives them, and an operator may configure other values for a source. A list-valued parameter, `MATCH_anyEPC`, `eventType` or `EQ_eventID`, is sent as one parameter whose values are separated by `|`, as the interface description declares. For a source that reads only a repeated parameter an operator may configure repetition for that source; it is off by default, it changes no recorded query, and the pull record and every result disclose it as a leniency. An answer that names no EPCIS wire version, or one this profile does not read, is refused before retention, and a document's `schemaVersion` is not read in its place. No provider-specific parameter is the standard query interface.

Credentials and permitted origins are server configuration. Every redirect and every pagination target is revalidated against the permitted origins; a credential is never forwarded to another origin; plain `http`, private-network targets and DNS rebinding are refused except under an explicit local-test configuration, which every result discloses; the same bounded loader policy governs contexts, DID documents and status resources. A page is checkpointed only after its imports and their results are durable. After an interruption the same configured query continues from its checkpoint. When the page token has expired, is rejected or is missing, a bounded replay from the query's retained bounds, with deduplication, resumes that query: it is never begun as a new source, and it skips no page that was not acknowledged. A configured query is bound to the address it was first run against, so the same query name pointed at another address is refused. When the same source is reached at another address, its operator declares the change once; the declaration is recorded in the pull record, the source scope, the pull and everything retained under them keep their identities, and a cursor is kept only when its address is permitted under the new configuration. A different underlying source takes a distinct source scope and is never remapped onto an existing one.

Each pull reports one of eight outcomes and they are never mistaken for one another: `source-link-missing` when discovery found no EPCIS link; `source-authentication-required` when the source demanded credentials; `source-forbidden` when it refused this caller; `source-unavailable` when it did not answer or answered an error; `unexpected-media-type` when it answered something that is not EPCIS, which is what an HTML sign-in page with status 200 is; `invalid-source` when the bytes were refused before retention; `partial-history` when the bounded query ended before the source did; and `ok` when the bounded query completed. A completed query that matched nothing is `ok` with an empty event list. Every result declares the selected subject, the query, the source and its completeness limits; a bound on record time cannot discover every retrospective error declaration, an exact-subject query does not retrieve the ancestral transformations of its inputs, and retrieving further identifiers requires explicit scope. Subscriptions, guaranteed synchronisation and a repository crawler are outside this profile.

## 4. Routes

This profile fixes no service interface or HTTP routes. An application that offers import, pull, retrieval or export over HTTP documents its own routes; the reference application documents the ones it serves. What an import does, whatever its interface, is sections 1 to 3 and 7.

## 5. Mapping into the VSC profile

**Parked.** This section binds only an implementation that selects `epcis-vsc@1` or `epcis-vsc@2`; see the status note at the top of this document.

`mapEpcisEvent` and its round-trip extension `urn:bsv:vsc:vocab:epcis-roundtrip:0.1.0` are unchanged. `mapEpcisEventWithReport` wraps them and returns, under the mapping profile it is asked for (`epcis-vsc@1` unless `epcis-vsc@2` is selected), one of four outcomes with its reasons: `lossless` when the event carries nothing the profile cannot express, so the SEAL's event vector and the round-trip extension together carry every source member; `transformed` when the event carries semantics the event vector does not, each named after a mapping limit of the profile manifest (parties, business transactions, sensor elements, quantities, persistent dispositions, master data, certification references, error declarations, transformation identifiers, event-level contexts, extension members, multi-product events, a caller-decided transformation action); `unsupported` when the profile cannot express the event or a decision is missing (an extension event type, a `TransformationEvent` without an explicit action decision, an action outside `ADD`, `OBSERVE` and `DELETE`, a disposition the custody model does not name, an inspection, repair or sensor reading observed by an `OBSERVE` event or a `TransformationEvent` that reports `active`, which `epcis-vsc@1` names `maintenance-observation`, an identifier scheme the profile does not carry); and `insufficient-data` when the source lacks an input the mapping never fabricates (`eventTime`, `eventTimeZoneOffset`, `bizStep`, `disposition`, a recorded time, a product identifier). Retention alone is never a lossless claim.

`epcis-vsc@2` changes how the disposition is decided, and refuses error declarations. After the event type and the action, an event carrying an `errorDeclaration` is `unsupported` as `error-declaration` (section 6). Then, before a SEAL is built, the disposition passes through the crosswalk its profile manifest records for every CBV 2.0 disposition of section 7.2.3, a value section 7.2.3.1 deprecates being treated as the value that replaces it, and for the business steps `receiving` and `accepting`. Five values are custody states the VSC custody model names by the same term, and the SEAL carries them verbatim where the event's type and action agree with the state: `active`, the origin, only on an `ObjectEvent` whose action is `ADD`, which commissions its objects (EPCIS 2.0 section 7.4.2); `in_transit` and `returned`, transit, on any event but an `ObjectEvent` that commissions or decommissions its objects; `dispensed` and `destroyed`, terminal, on any event but an `ObjectEvent` that commissions them. On the other event types `ADD` and `DELETE` add objects that already exist to, or remove them from, an aggregation, an association or a business transaction; and a `TransformationEvent`'s SEAL carries its inputs, which exist before it. Every other event is `unsupported`, its reason opening with the id of the mapping limit it cites: `custody-neutral` for a disposition that records a condition and no custody state (`conformant`, `non_conformant`, `damaged`, `needs_replacement`, `in_progress`, `sellable_accessible`, `recalled` and the rest the crosswalk lists), for `active` on any event but a commissioning `ObjectEvent`, and for an `OBSERVE` event without a disposition, which EPCIS 2.0 section 7.3.6.2.1 reads as unchanged; `custody-destination-unnamed` in place of `custody-neutral` at a `receiving` or `accepting` step, a hand-over at the destination whose only VSC term, `received`, is not a CBV disposition; `lifecycle-conflict` for a transit or terminal disposition on an `ObjectEvent` that commissions its objects, which can only open their custody chain at the origin, and for a transit disposition on one that decommissions them, after which they do not exist; `custody-transition-unnamed` for `retail_sold`, `partially_dispensed`, `disposed`, `inactive` and `stolen`, custody changes for which no VSC term is a CBV value; and `non-cbv-disposition` for a value that is not a CBV 2.0 disposition in its bare, URN or Web URI spelling. An `ADD` or `DELETE` event without a disposition stays `insufficient-data`. The limit id is the contract; the words after it are the build's own. After the crosswalk, the remaining checks and the named losses are those of `epcis-vsc@1` without its `maintenance-observation` rule, which the crosswalk replaces; `epcis-vsc@1` stays selectable and is the default.

Under `epcis-vsc@2` a custody-neutral event has no SEAL, because none can be issued without changing the VSC profile. The SEAL schema requires a disposition from the nine custody terms on every SEAL; verification reads each SEAL's custody state from that disposition, permits a same-state step only in transit, and makes a SEAL without parents the origin of a new chain ([`vsc-profile.md`](vsc-profile.md) section 5); and the VSC Core draft requires every disposition to map to a state. A neutral value is none of the nine terms, so a SEAL for an inspection outcome, a condition or an observation would be refused, would assert a custody state the event did not record, or, carrying `active`, would open a new custody chain for objects that already exist. The event stays evidence, and the custody rules are not bent to admit it. `epcis-vsc@1` still maps an event that reports `active` without commissioning its objects, other than the maintenance observations it refuses, as its published vectors pin; that SEAL passes custody verification only as the origin of a new chain.

`stored`, `transshipped`, `transformed` (transit) and `received` (the destination) are VSC draft terms, not CBV dispositions. They remain valid in `vsc-draft-compat@0.1.0` for a SEAL issued directly under that profile, and `epcis-vsc@1` carries them when an event spells them; `epcis-vsc@2` refuses them as `non-cbv-disposition` and never writes one for a CBV event. Because CBV has no disposition for the destination, a chain of SEALs mapped under `epcis-vsc@2` never reaches it: a mapped `dispensed` or `destroyed` SEAL passes custody verification only after a destination SEAL issued directly under the VSC profile, and a mapped `returned` that follows the destination also needs the issuer's `returnReason` extension.

A mapped SEAL carries, beside the round-trip event, the signed source reference `urn:bsv:dpp:epcis-source:1`: the digest and media type of the exact source bytes, the event's pointer, its `eventID` when present, the sorted digests of the contexts it was read under, and the mapping profile, which is the one the report was made under; a reference naming another profile is refused. The reference lets a verifier fetch the retained bytes, locate the event and recompute its body digest; it asserts nothing about the source's truth.

The SEAL's actor is the signing issuer. A party the event names in its source list, destination list or business location is retained in the extension and never projected into `who`; an issuer that attests to receiving another party's report is not thereby attesting that it performed the physical event. Issuance is a separate, separately authorised step that requires the actual issuer and assertion key, role, jurisdiction, status entry and custody evidence, and the complete SEAL is then evaluated under the VSC profile including its Q-state transitions, subject continuity and correction rules. Those rules are not changed to admit a maintenance observation or a multi-product event; an event that is valid EPCIS and unpublishable as this profile stays access-controlled evidence with an explicit outcome, is not submitted to the secured-credential endpoint, and is never relabelled as a signed claim.

## 6. Error declarations and corrections

**Partly parked.** The retention, reporting and resolution of an error declaration belong to the source exchange and stand. What each mapping profile does with an event that carries one is parked with section 5.

An `errorDeclaration` is retained with its declaration time, reason and corrective event references and reported per event. An event that carries one asserts that the prior event it repeats is in error, not that its step happened (EPCIS 2.0 section 7.4.1.2): under `epcis-vsc@2` it is `unsupported` as `error-declaration` and has no SEAL, because a SEAL would assert the step the source retracted, while `epcis-vsc@1` maps it with the loss `error-declaration`, as its manifest publishes. A corrective event is an ordinary event and maps as one. It is resolved only when every corrective event it names is held under the same source, in the same document or one retained earlier; otherwise it is unresolved and stays so. A corrective event held under another source resolves nothing. An EPCIS error declaration is not a VSC `correctionOf` and grants no correction authority: a VSC correction requires the existing issuer or a verified scoped delegate, the correction chain and the reason evidence of [`vsc-profile.md`](vsc-profile.md) section 5. Competing corrections remain conflicts; earlier signed bytes are retained.

## 7. Tokens, publication and recovery

No import, pull, mapping or export invokes `ISSUE`, `UPDATE`, `TRANSFER` or `RETIRE`. Shipping, receiving, owning-party and possessing-party fields establish neither token authority nor recipient acceptance. A later business workflow MAY cite retained source evidence when it calls the passport service; that service independently validates the current tip, the actor's authority and the recipient's acceptance. Retiring a token does not erase the event store and does not prevent a separately authorised later attestation.

A publication persists the immutable issued credential and its identifier before submitting it for anchoring, and records the durable operation it runs under. A retry after an uncertain answer queries the existing credential and anchor result through the existing journal and recovery interfaces; it never issues a fresh credential or spends again blindly.

## 8. Operational recovery

An operator that moves an exchange to another store, or leaves a provider, needs more than the EPCIS documents. An authorised recovery snapshot carries, for each source scope it covers, every retained original in its exact bytes and the durable records that no source can rebuild: each import record with its `sourceId`, its `importId`, its `requestId` bound to `requestDigest`, its stored results, its receipt time and provenance and its context, profile and policy references; each observation; each conflict decision with every competing observation it names; and each pull record with its query definition and bounds, the limits in force, how its latest run ended, the pass under way, its watermark and its checkpoint, beside the record of every page it acknowledged and the import that holds that page. The associations index and the retention entries are derived and are not carried: the destination rebuilds them. The journal of unfinished work is not carried either, because a snapshot is taken only when it is empty. A bounded export about one passport is not a recovery snapshot: a pull and a conflict belong to a source scope, whatever passports their events name.

A snapshot is taken at a boundary. No unfinished work is journalled when it is taken, and everything it carries stood together at one moment: it never holds a checkpoint without the imports and page records that checkpoint stands on, or a decision without every observation it decided between. An exporter that cannot establish such a boundary refuses and says why; it does not finish or discard unfinished work as a side effect of exporting. Before a snapshot is handed over it is held, taken by itself, to the invariants of the exchange.

A snapshot is carried in the evidence envelope of [`portable-evidence.md`](portable-evidence.md) section 2 and is not another export format: each original and each record is one file with one inventory entry, beside a descriptor, `epcis-recovery.json`, conforming to [`../contracts/epcis-recovery.schema.json`](../contracts/epcis-recovery.schema.json). The descriptor names every file the snapshot needs with its length and digest, the source scopes covered with what each holds, the boundary, everything left out with the reason, and what is claimed: complete for the covered scopes and recoverable, or bounded. Its identity is the digest of the inventory it names, so the same content has the same identity whenever it was exported. A record is written in RFC 8785 canonical form, so one record has one spelling.

Recovery and public evidence are different access paths. A recovery snapshot is for the operator authorised to run the exchange. A public package carries only the originals its access policy allows, each with its import record reduced to what a public reader may see: where and how a source was read is left out, and no observation, decision or pull state is carried. Such a form says it is public, claims no completeness, and cannot be restored. No credential, key or address that holds a secret enters either form. A cursor, and the page token a page was asked for with, is authorised recovery data that may be sensitive: by default a snapshot carries none, and an unfinished pass then resumes at the destination through the bounded replay of section 3. An operator may ask for cursors to be carried; one whose address holds anything but the standard query parameters is left out even then, and a carried cursor is checked against the permitted origins again before it is used.

A restore trusts nothing because it was carried. Before anything is written it checks the descriptor against the inventory of the package, every file against its length and digest, every record against its version and against the place its own content gives it, the records against what the descriptor says of each scope, each pull and the cursors, and the whole snapshot against the invariants. A snapshot whose descriptor says cursors were left out and whose records carry a cursor or a page token is refused, as is one that carries a cursor whose address holds more than the standard query parameters. Each failure has its own name: a pull whose checkpoint stands on an omitted import or page; a decision whose observation is omitted; an original that is missing, and one that is altered; a record that is missing, and one that is altered; a descriptor that does not match the inventory; a record of an unknown version; a record filed as something it is not; a public form offered for restore. A restore then compares the destination with the snapshot. A destination record equal to the snapshot's is left as it is, so a restore that stopped at any durable step is run again and finishes. One that differs under the same identity is never overwritten: the restore stops before writing and reports each collision, a request bound to other bytes among them, for the operator to reconcile. Two source scopes are never merged because they share an event identifier or an endpoint, and a snapshot in which a record of one scope stands on a record of another, a page on another scope's import of the same bytes or an observation on another scope's import, is refused.

A restore preserves every logical identity, every receipt time, the provenance, the recorded results and the decisions, and restores them as they were recorded: a later re-evaluation of a source is a separate, labelled result and replaces nothing. Only `bytesRef`, which says where a store keeps the bytes, takes the destination's value, through a mapping that pairs each exported reference with one original and each original with one destination reference. Every original is read back from the destination and held to its digest. The snapshot itself is never changed; the destination records which snapshot it restored and where each original was placed. Because the request binding is restored with its result, a retry of a request that was acknowledged before the move answers the same import and writes no receipt, and the same request identifier with other bytes still conflicts. Only the derived indexes are rebuilt, and the destination is then held to the invariants. While a restore is unfinished the store says so, and a snapshot of it is refused.

Credentials and endpoint configuration are provisioned at the destination, separately from the snapshot, before a pull is run. An interrupted pull then continues as the same configured query under the same source scope: from a carried cursor that is still permitted and usable, or by replay from its retained bounds, with deduplication, when the cursor was left out, has expired or is rejected by the source. A carried cursor whose address the destination's configuration does not permit is never requested; the run says so, and the operator's declaration of the source's address and permitted origins drops that cursor, after which the pass replays from its bounds. In every case the pull skips no page that was not acknowledged and begins no new source.

## 9. Normative and implementation

What a conforming party reproduces: the supported inputs, the refusals before retention, the retention-with-findings rule and the disclosed limits (section 1); the retained source contract, the scoped identities, the body digest and the arrival classification (section 2); the standard query consumption, the loader policy and the eight outcomes (section 3); the four mapping outcomes under each mapping profile, the `epcis-vsc@2` crosswalk with its conditions, its business-step replacement and its refusals by name, the source reference and the attribution rule (section 5); the treatment of error declarations (section 6); the separation from token operations and the publication recovery rule (section 7); and, for a party that offers recovery, what a snapshot carries and leaves out, the boundary it is taken at, its descriptor, the separation of the public form, the exclusion of credentials and the default exclusion of cursors, the checks a restore makes before it writes, the preservation of identities with a checked relocation of byte references, the refusal to overwrite and the resumption rules (section 8). The mapping and publication rules among them bind only a party that selects a parked mapping profile. What is a build's own: its service interface and HTTP routes, where bytes are retained, which store holds the import record, how a store establishes the boundary of a snapshot, the names the files of a snapshot have under its folder and the names of its refusals, which automation policy may request publication, which limits an operator lowers or raises within the profile's bounds and the ceiling a build sets on a raised one, the finer reason a build names under one of the eight outcomes, and the departures from a strict reading of the query interface that a build accepts, provided each is recorded and none changes what is retained. A recovery snapshot moves an exchange between stores of one build. Its records carry identifiers that build derives, so no claim is made that a snapshot written by one implementation restores into another.
