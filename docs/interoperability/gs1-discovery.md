# GS1 discovery

**Profile:** `gs1-digital-link@1`. **Canonical sources:** [`spec/gs1-discovery.md`](https://github.com/bsv-blockchain/dpp/blob/main/spec/gs1-discovery.md), [`packages/dpp-profiles/manifests/interoperability/gs1-digital-link@1.json`](https://github.com/bsv-blockchain/dpp/blob/main/packages/dpp-profiles/manifests/interoperability/gs1-digital-link@1.json), [`fixtures/vectors/dpp/interoperability/gs1/`](https://github.com/bsv-blockchain/dpp/blob/main/fixtures/vectors/dpp/interoperability/gs1/README.md), [`docs/identifiers.md`](../identifiers.md). **Example:** `node examples/resolve-digital-link.mjs`.

A passport identifier is a GS1 Digital Link URI, and this profile is how a scan reaches a passport. It fixes the grammar for primary key 01 with the consumer product variant, lot and serial qualifiers and data attributes; key-tuple equivalence, so the same path names the same item at every host and a serial is never joined under another GTIN; EPC-binary decompression for SGTIN-96 and SGTIN-198 with the compression standard's own worked examples as vectors; resolution records with the resolver standard's hierarchy, so a serial request answered by a model record is labelled model information; linkset production and selection validated against the pinned GS1 resolver schemas; and the resolver description file.

The reference registry hosts a GS1-Conformant Resolver on a configured origin, keeps the legacy evidence route on the API origin and aliases it, so no printed code changes. A deployment that names an external resolver runs none of its own and reads it through the same discovery client. The vectors cover URI syntax (6 positive, 10 refusal), EPC binary (4 and 4) and resolution (12 and 4).

Discovery finds a passport; it verifies nothing. A resolved link is where to fetch bytes, and the reader still holds them to the record rules and its header source. And a GTIN that parses with a correct check digit is not thereby allocated to the brand the record describes.
