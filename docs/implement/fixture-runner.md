# Running the fixtures

**Audience:** an implementer building a test harness. **Canonical sources:** [`fixtures/README.md`](https://github.com/bsv-blockchain/dpp/blob/main/fixtures/README.md), [`fixtures/vectors/dpp/interoperability/README.md`](https://github.com/bsv-blockchain/dpp/blob/main/fixtures/vectors/dpp/interoperability/README.md), the vector format of the BSV stack (`conformance/VECTOR-FORMAT.md` in `bsv-blockchain/ts-stack`).

## Two forms, one set of bytes

The bespoke JSON files at the top of `fixtures/` are one object per format with every pinned value a property and the refusal variants beside them. The files under `fixtures/vectors/` hold the same bytes in the stack's cross-language vector format. Both are generated by the reference test suites and neither is edited by hand; a difference between the two forms is a generation defect. Vendor both verbatim, assert against them in your own suite, and fix a divergence in your implementation, never in the fixture.

## What a harness does

1. **Reads the vector files generically.** Each file has `id`, `version`, `reference_impl`, `parity_class` and `vectors[]`; each vector has `id`, `input`, `expected` and `tags`. A structural runner from the stack validates the files as they stand; yours executes them.
2. **Executes every vector as a predicate.** A positive vector's expected bytes must be reproduced or verified; a refusal vector must be refused at the point the vector names. A vector that is not executed is reported as not executed, never counted as passed.
3. **Runs the bespoke files where the vectors do not reach.** The chain fixtures' `refusals[]` name the prefix each extends and the option under which it is refused; the report fixtures name declared observers and header sources a harness answers as written; the acceptance fixture's refusals answer three verdicts separately.
4. **Injects the observation time.** The report fixtures carry `checkedAt`; a harness injects it so `checkedAt` and `observedAt` compare equal across implementations, never the wall clock of a test.
5. **Reports one sentence per vector.** Refusals included, no aggregate score, in the fixture's own words.

## The files by role

| Role | Bespoke | Vectors |
|---|---|---|
| Passport reader | `record-v1`, `chain-v1`, `evidence-v1`, `record-v2`, `chain-v2`, `managed-acceptance-v1`, `evidence-v2` | `record/v1`, `record/v2`, `chain/v1`, `chain/v2`, `managed-acceptance/v1` |
| Attestation verifier | `attestation-anchor-v1`, `anchor-v3`, the anchor cases of `evidence-v1` | `attestation-anchor/v1`, `anchor/v3` |
| Passport writer, attestation issuer | The positive members of the above, reproduced from the published keys | The `happy-path` vectors |
| Registry, overlay | `attestation-anchor-v1`, `chain-v2` | `publisher-policy/v1`, `evidence-package/v1`, and the vector runner over everything |
| Profiles and interoperability, when claimed | `battery-lifecycle-v1` | `interoperability/gs1/*`, `interoperability/epcis/v1`, `interoperability/external-credential/v1`, `interoperability/projection/*` |

## What the fixtures do not certify

Writer behaviour (self-reported), operator behaviour under load or partition (the demonstration), the truth of any claim, and anything about a profile's legal adequacy. A harness that passes every byte vector has shown agreement on bytes and refusals, which is exactly what the fixtures exist to settle.
