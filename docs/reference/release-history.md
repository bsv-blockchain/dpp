# Release history

Maintainers and auditors checking an older installation can use this page to find an earlier release set, when it was published, what it published and the receipt that records it. It is the one record of publication history: the [release guide](release-sets.md) describes the current set and how to verify the last publication, and the changelog points here. For a new implementation, choose the [current set](release-sets.md#the-current-set).

## Where the records are kept

| Record | Location |
|---|---|
| Every superseded set | `release/archive/<set>.json` in the repository, byte for byte as it was when superseded |
| The selection that qualified it | `release/archive/selections/<set>.json`, byte for byte |
| Receipts and approved plans | `docs/reference/publication-history/`, linked from the table below; each plan is the approved JSON, byte for byte |

The archived files are never edited. Each approved plan records its selection's digest, which the archived selection still matches. A plan also records its set's digest at the source revision it bound, before the set was marked superseded, so each set link below opens the set at a recorded revision: for a set published under an approved plan, the source revision that plan bound, the revision to reproduce it from. The archived link beside it opens the file under `release/archive/`.

## Adding a publication

When a set is published, its receipt and approved plan join `publication-history/`. When it is superseded, it gains a row here, and it and its selection move to `release/archive/` and `release/archive/selections/`, where they are not edited again; `conformance/check.mjs` refuses a superseded set or selection left beside the current one. [Publish a package update](publishing-profile-updates.md#keep-release-navigation-current) is the procedure.
