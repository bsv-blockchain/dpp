# EPCIS interoperability vectors

`v1.json` pins the behaviour of the `epcis-json@1` source exchange profile and the `epcis-vsc@1` mapping profile (`spec/epcis-interoperability.md`) in the stack's vector format. Its source exchange vectors are generated by `packages/dpp-credentials/test/epcis-fixture.ts` and held identical to that generator by `packages/dpp-credentials/test/epcis-artefacts.test.ts`; change the generator and run that suite with `REGENERATE_FIXTURES=1` to move them, and review the diff. Its two mapping vectors, `mapping-outcomes` and `evidence-only-and-attribution`, and the whole of `v2.json` belong to the parked mapping profiles, whose code left `@bsv/dpp-credentials` in 0.2.0-beta.6: they stay as published, held by digest in the same suite, and their generators stay in the repository history at commit `8c82c5e6ca31cd991e701d1051047153c7395eae`.

Every identifier is synthetic. GS1 keys use the demonstration prefix 952, which GS1 reserves for examples and never licenses; hosts are under `example.org`; the issuer is `did:web:issuer.example`. Nothing was copied from any published event source, and none of these documents describes a real product.

| Vector | What it proves |
|---|---|
| `five-event-document` | A valid `EPCISDocument` with all five event types: a two-stage `TransformationEvent` chain (cells into a module, the module and an electrolyte lot into a pack, scrap out), a commissioning `ObjectEvent`, an `AssociationEvent` that records the cells as members of the pack, an `AggregationEvent` that records the pack on a shipping container, a `TransactionEvent` with a purchase order and owning-party source and destination, and a sensor observation that carries no `eventID`. The expected result carries the source digest, the envelope facts, the pinned-schema outcome, every event's pointer, identity kind, event-body digest, classified identifiers and preserved extension members. |
| `query-document-page` | The same events under the `EPCISQueryDocument` envelope, located at the query-result pointer. |
| `event-body-digest-and-arrival` | The canonical event-body digest ignores formatting and member order, excludes `recordTime` and `errorDeclaration`, includes the sorted context digests; a changed `recordTime` or error declaration is a new observation, a changed body is a conflict. |
| `local-identity-without-event-id` | The local ingestion identity of an event without an `eventID`, derived from the source digest and pointer and never written into the source. |
| `error-declaration-resolved-and-unresolved` | An error declaration retained with its corrective references: resolved when the corrective event is held, unresolved when it is absent; never a VSC correction. |
| `schema-invalid-safe-transport` | A document the pinned schema rejects is safe to retain with failed findings, and is repaired by nobody. |
| `refuse-*` | Transports refused before anything is retained: a duplicate member name, malformed UTF-8, nesting past the depth limit, a number that overflows, a number whose digits a double loses, a document over the byte limit, more events than the per-document limit, an XML media type. The bytes are carried as hex because most of them are not JSON values. |
| `mapping-outcomes` | Each event of the five-event document mapped into the VSC profile with an explicit outcome: the commissioning event is `lossless` and yields a structurally valid unsigned SEAL carrying the `urn:bsv:dpp:epcis-source:1` reference; the others are `transformed` with their losses named or `unsupported` where the custody model names no state. No SEAL is issued. |
| `evidence-only-and-attribution` | Valid EPCIS without a disposition is `insufficient-data` and stays evidence; an event naming an owning party and a business location maps with the configured issuer as actor, never with the party the event names. |

A conforming implementation of the source profile reproduces the accepted and refused outcomes, the digests and the identities; a conforming implementation of the mapping profile reproduces the outcomes and, for the lossless case, a SEAL that passes the VSC structure validation with the same event vector and extensions. The SEALs in the file are unsigned by design: issuance is a separate, separately authorised step.

`v2.json` pins the `epcis-vsc@2` mapping profile, as published. The source exchange vectors stay in `v1.json`, which is unchanged.

| Vector | What it proves |
|---|---|
| `crosswalk-every-disposition` | Every CBV 2.0 disposition of section 7.2.3, and each value section 7.2.3.1 deprecates, in one `ObjectEvent` under `ADD`, `OBSERVE` and `DELETE`: `active` (under `ADD` only), `in_transit` and `returned` (under `OBSERVE` only), `dispensed` and `destroyed` (not under `ADD`) are carried verbatim; every other combination is `unsupported` under the mapping limit the profile manifest's crosswalk names. |
| `origin-and-lifecycle` | `active` is the origin only on an `ObjectEvent` that commissions its objects: on an aggregation, association or transaction that adds existing objects, and on a transformation, it is `custody-neutral`. A transit or terminal disposition on a commissioning `ObjectEvent`, and a transit one on a decommissioning `ObjectEvent`, is `lifecycle-conflict`; on the other event types `ADD` and `DELETE` leave them carried. |
| `disposition-spellings` | The bare, URN and Web URI spellings of one disposition map alike; the SEAL carries the CBV term and the round-trip extension the spelling received. |
| `non-cbv-dispositions` | The VSC-only terms `stored`, `transshipped`, `transformed` and `received`, a non-CBV value in the CBV namespace, a private URI and a value in the wrong case are `non-cbv-disposition` under `epcis-vsc@2`, beside what `epcis-vsc@1` answers for each. |
| `absent-disposition` | An `OBSERVE` event without a disposition is `custody-neutral` (`custody-destination-unnamed` at a receiving step); an `ADD` or `DELETE` event without one is `insufficient-data`. |
| `error-declarations` | An event carrying an error declaration is `error-declaration` under `epcis-vsc@2`, with no SEAL, and maps with the loss named under `epcis-vsc@1`; the corrective event maps under both. |
| `custody-destination` | A receiving or accepting step whose disposition is neutral, `active` or absent is `custody-destination-unnamed`, because the destination's only VSC term is not a CBV value; `returned` at a receiving step maps, `retail_sold` is `custody-transition-unnamed`. |
| `maintenance-observations-under-both-profiles` | The same inspections, repairs and sensor readings under both profiles: `epcis-vsc@1` refuses those observed reporting `active` as `maintenance-observation` and maps those reporting a custody state and a commissioning event at a repair step; `epcis-vsc@2` refuses every observation reporting `active`, a repair recorded as a transformation among them, as `custody-neutral`. |
| `mapping-outcomes` | The five-event document of `v1.json` mapped under `epcis-vsc@2` with source references that name it: the commissioning event is lossless, the assembling transformations reporting `in_progress` and the association reporting `active` are `custody-neutral`, the rest map with their losses named. |
| `attribution` | A mapped event that names an owning party and a business location carries the configured issuer as actor, never the party. |

A conforming implementation of `epcis-vsc@2` reproduces every outcome and every limit id; the prose after the limit id is the reference implementation's and is not part of the contract.
