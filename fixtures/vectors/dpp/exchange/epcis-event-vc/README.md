# epcis-event-vc@1 credential vectors

`v1.json` pins the credential of the proposed exchange profile `epcis-event-vc@1` (`spec/epcis-event-profile.md`): a GS1 EPCIS 2.0 event as a W3C Verifiable Credential 2.0 whose `id` is the event's CBV 2.0 Event Hash ID, secured as a compact JWS under ES256K by the party's one published credential key. It is generated by `packages/dpp-protocol/test/epcis-event-vectors.ts` and held identical to its generator by `packages/dpp-protocol/test/epcis-event-vectors.test.ts`; change the generator and run that suite with `REGENERATE_FIXTURES=1` to move it, and review the diff. The hash vectors it rests on are `../../interoperability/epcis/hash-v1.json`.

Two parties sign. Their identity key scalars are published under `keys`, each credential key is the BRC-42 child of the identity key under `[1, 'dpp epcis event v1']` with key identifier `credential` and counterparty anyone, and each issuer is the `did:key` of that credential key. Every identifier is synthetic: GS1 keys under the demonstration prefix 952, hosts under example.org. Nothing derived from the scalars will ever hold value. `checked_at` is fixed so the time findings reproduce.

| Vector | What it proves |
|---|---|
| `positive` | The commissioning event signed by party A: the hash ID is the credential `id`, the signature verifies from the `did:key` alone, the interval includes `checked_at`, no status entry, no authority policy; the anchor fields a registry writes. |
| `re-encoded-copy` | The same credential serialised differently by the same party: another byte string and digest, the same `id`, a proof that holds, and a registry refusal under the pair rule. |
| `second-issuer` | The same event signed by party B: a second attestation of one hash ID, accepted. |
| `tampered-record-time`, `tampered-biz-step` | A changed `recordTime` leaves the hash intact and fails the signature; a changed `bizStep` fails the hash, reported first. |
| `kid-of-another-party`, `event-id-not-its-hash`, `error-declaration`, `unsupported-identifier` | Refusals by name: a `kid` outside the issuer, a subject contradicting its `id`, an error declaration, an EPC scheme outside the subset. |
| `multi-object-subject`, `sensor-event-with-extension-context` | The subjects are the object identifiers only, sorted, the anchor subject the first; an inline prefix declaration as the third context entry. |
| `not-yet-valid`, `expired`, `status-entry-without-verifier` | The time findings, and a status entry left `unknown` without a verifier. |
| `alg-es256`, `malformed-two-parts`, `unknown-credential-member` | Another suite is unsupported, not failed; a malformed serialisation and a member the profile does not define are shape failures. |
| `did-web-issuer-with-resolver` | A `did:web` issuer whose `kid` resolves through the caller's resolver, and the `unknown` proof without one. |

A conforming verifier reproduces every finding, the hash ID, the subjects and the anchor fields; a conforming writer, given the scalars, reproduces the positive JWS byte for byte, because ES256K signatures here are deterministic (RFC 6979).
