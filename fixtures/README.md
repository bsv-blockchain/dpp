# Conformance fixtures

**Status: the seed of the conformance suite, not the suite.** These files pin wire formats byte for byte, so that independent implementations that cannot import one another stay in agreement by testing against the same bytes. A fixture is not an elegant contract, but it is the kind that fails loudly: change a field order, a canonicalisation rule, a protocol string or a signing preimage anywhere, and a suite goes red with a diff you can read.

Two rules these files follow, and any future fixture must:

1. **Refusal vectors are part of the fixture.** A fixture with only positive vectors certifies that an implementation accepts what it should, and never that it refuses what it must. Every fixture that pins a signed layout carries variants a conforming reader is required to reject.
2. **Copies are verbatim.** Implementations vendor these files unchanged and assert against them in their own suites. Fixing a divergence means changing the implementation, never the fixture, unless the specification itself has changed, in which case the format's version identifier changes with it.

## Two forms, one per format

The JSON files at the top of this directory are the bespoke form: one object per format, every pinned value a property, refusal variants beside them. `vectors/` holds the formats that have no bespoke object, in the BSV stack's cross-language conformance vector format (`conformance/VECTOR-FORMAT.md` and `conformance/schema/vector.schema.json` in `bsv-blockchain/ts-stack`): a file with a stable dotted identifier, a version, the reference implementation that produced it and a parity class, holding vectors that each carry an identifier, an input, an expected result and tags. Positive vectors are tagged `happy-path`, refusals `error-case`, and binary is lower-case hex under keys ending `_hex`. Any runner that reads the stack's corpus reads these, and the stack's structural runner validates them as they stand: `node conformance/runner/src/runner.js --validate-only --vectors <this directory>/vectors` from a checkout of `ts-stack` with the runner's dependencies installed, exit code 0 clean, 2 malformed. A format is published in one form here, with one exception: the current anchor, whose bespoke file pins its bytes and whose vector file [`vectors/dpp/attestation-anchor/v1.json`](vectors/dpp/attestation-anchor/v1.json) also pins the six refusals the bespoke file does not carry.

Both forms are generated by the packages' tests, as each section below names, and neither is edited by hand: a test in each package holds every published file identical to what its generator produces. To change a published file, change the module that generates it and run the suites with `REGENERATE_FIXTURES=1`, which rewrites the files before comparing them; the diff is the review. Vector identifiers are permanent once published, and a file is append-only while it stays published: a corrected expectation is a new vector, and the old one is marked skipped with a reason, which is the stack's rule and this directory's. A file retired whole, as the next paragraph records, takes its identifiers with it, and they are not reused.

Until 12 November 2026 `vectors/dpp/` also restated eight bespoke files in the vector form: `record/v1.json`, `record/v2.json`, `chain/v1.json`, `chain/v2.json`, `anchor/v3.json`, `managed-acceptance/v1.json`, `managed-acceptance/v2.json` and `index-registration/v1.json`. Each was a mapping of a file in this directory, so they were removed, and their last copies are at commit [`c678cf9`](https://github.com/bsv-blockchain/dpp/tree/c678cf9281168179d16d599e5fdb3846ddbbaf61/fixtures/vectors/dpp). Two things they carried that the bespoke files do not are kept. The synthetic test private keys, so that a writer in any language reproduces the pinned bytes rather than only checking them, each a byte repeated to 32 bytes: `11` (actor), `22` (service) and `33` (owner) for `record-v1.json`, the same with `44` and `55` for the second and third owners of `chain-v1.json`; `11` (issuer), `22` (custodian, the publisher), `33` (recipient), `44` (a stranger) and `55` (a control authority) for `record-v2.json` and `chain-v2.json`; `22`, the custodian, for both acceptance records; `33`, the application's publisher key, for `index-registration-v1.json`; and `77` (the anchoring service) and `88` (the issuer) for both anchors, which `attestation-anchor-v1.json` also carries. Nothing derived from these keys will ever hold value. And the four length-bound refusals of the historical anchor, which `anchor/v3.json` built from the pinned output: they are no longer pinned bytes but a test, one over each of the three bounds in [`../spec/legacy-uora-anchor-v3.md`](../spec/legacy-uora-anchor-v3.md) §5 and a claim whose `passportId` exceeds the bound §3 sets, which `packages/dpp-overlay/test/anchor-v3-bounds.test.ts` builds, so the bespoke file the implementing repositories hold verbatim is unchanged. A reader in another language builds them the same way: each is the pinned `lockingScript` with one field one byte over its bound and the signature untouched, and the last a correctly signed anchor over a claim whose `passportId` is one byte over. The current anchor's vector file was not retired, because its six refusals are in no other published file.

A conformance report over these vectors is presented as [`../GOVERNANCE.md`](../GOVERNANCE.md) requires: one sentence per vector, refusals included, and no aggregate score. The runner's per-vector output is the data; the sentences are the presentation.

## `anchor-v3.json`

One complete `uora-anchor-v3` anchor, from the attestation claim through its canonical bytes, digest, derived locking key and full locking script, as [`../spec/legacy-uora-anchor-v3.md`](../spec/legacy-uora-anchor-v3.md) defines. The leading copy is [`../packages/dpp-overlay/test/anchor-v3-fixture.ts`](../packages/dpp-overlay/test/anchor-v3-fixture.ts); this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys involved are test keys, published deliberately; nothing derived from them will ever hold value.

| Property | What it pins |
|---|---|
| `attestation` | The claim exactly as posted, signed properties included. |
| `canonical` | The canonical bytes of that claim, as a string (spec §4). |
| `digest` | SHA-256 of the canonical bytes: the anchor's field 2. |
| `issuerDid`, `issuerKey` | The claiming party's two names for one key. |
| `anchoredBy` | The anchoring service's identity key: field 7. |
| `lockingKey` | The BRC-42 child the output must lock to, reproducible from `anchoredBy` and the attestation id. |
| `lockingScript` | The whole output, hex. Deterministic: signatures use RFC 6979 nonces, so this is reproducible on any machine from the test keys. |
| `boundaryShifted` | Four re-cut variants of the same output with the signature bytes untouched. Every one must be refused. They all verified under the superseded layout, which is why the current one exists. |
| `uncompressedKey` | The same output with its locking key re-pushed in the 65-byte uncompressed spelling. Attribution still matches after decoding, which is exactly why a lenient reader admitted it invisibly; a conforming reader refuses it at the push. |
| `malformedTail` | The same output with its drop tail wrong three ways: one drop short, the right total in the wrong opcodes, and a trailing chunk after a correct tail. A conforming reader validates the tail exactly and refuses each. |

A conforming writer reproduces `lockingScript` from `attestation` and the test keys. A conforming reader parses `lockingScript` to the fields above, verifies the field-8 signature over the SHA-256 of the length-delimited preimage, checks the locking key, and refuses every script in `boundaryShifted`, `uncompressedKey` and `malformedTail`. It also refuses the four length-bound variants that `packages/dpp-overlay/test/anchor-v3-bounds.test.ts` builds from `lockingScript`, which no file pins.

## `record-v1.json`

One complete DPP record-model v1 output, from the posted state through its signing preimages, signatures, derived verification keys and full locking script, as [`../spec/record-model.md`](../spec/record-model.md) defines. The leading copy is [`../packages/dpp-protocol/test/record-v1-fixture.ts`](../packages/dpp-protocol/test/record-v1-fixture.ts), whose neighbouring tests rebuild every pinned byte from `state` and the test keys; this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys involved are test keys, published deliberately; nothing derived from them will ever hold value.

| Property | What it pins |
|---|---|
| `state` | The twelve data fields exactly as posted. |
| `ownerBlob` | The off-chain owner-tier blob whose SHA-256 is field 11 (spec §7). |
| `userPreimage`, `serverPreimage` | The two signing preimages: fields 1 to 12 concatenated raw, then the same followed by the user signature bytes (spec §5). |
| `userSignature`, `serverSignature` | DER ECDSA over SHA-256 of the preimages. Deterministic: RFC 6979 nonces, so both are reproducible on any machine from the test keys. |
| `userVerificationKey`, `serverVerificationKey` | The BRC-42 children the signatures verify under, re-derivable from on-chain data plus the published service identity (spec §5). |
| `lockingKey`, `lockingScript` | The whole output: key push, `OP_CHECKSIG`, fourteen minimal pushes, seven `OP_2DROP` (spec §2). |
| `uncompressedKey` | The same output with its locking key re-pushed in the 65-byte uncompressed spelling; a conforming reader refuses it at the push. |
| `malformedTail` | The drop tail wrong three ways: one drop short, the right drop total in the wrong opcodes, and a trailing chunk after a correct tail. A conforming reader validates the tail exactly and refuses each. |
| `rolledTimestamp` | Field 5 as `2026-02-30T00:00:00Z`, a date the calendar does not contain; hosts that roll it into March accepted it invisibly. Refused at decode. |
| `mangledUtf8` | `payload_public` as the bytes `22 ff 22`: invalid UTF-8 whose lossy decode is the valid JSON string `"�"`. Refused at the bytes, not after them. |
| `nulPassportId` | `passport_id` pushed non-minimally as the single byte `0x00`, which no field may be: minimal writing spells that value `OP_0`, and `OP_0` reads back as the empty field. Refused. |
| `emptyPushdata` | `event_data`'s `OP_0` re-encoded as a zero-length `PUSHDATA1`; `OP_0` is the only accepted encoding of the empty field. Refused. |
| `overlongPassportId` | `passport_id` at 513 bytes, one over the bound spec §3 sets because the field is a BRC-42 key identifier and a conforming wallet has a ceiling. Refused at decode, before any signature is checked. |

A conforming writer reproduces `lockingScript` from `state` and the test keys. A conforming reader parses `lockingScript` back to the state, verifies the user signature under `userVerificationKey`, and refuses every script in `uncompressedKey`, `malformedTail`, `rolledTimestamp`, `mangledUtf8`, `nulPassportId`, `emptyPushdata` and `overlongPassportId`.

## `chain-v1.json`

One complete DPP record-model v1 passport chain, six states long, and the broken links a verifier must refuse, as [`../spec/record-model.md`](../spec/record-model.md) §6 and [`../spec/custody.md`](../spec/custody.md) §3 define. `record-v1.json` pins one output; this pins what holds outputs together, and how an owner's own wallet holds and hands over a passport. The leading copy is [`../packages/dpp-protocol/test/chain-v1-fixture.ts`](../packages/dpp-protocol/test/chain-v1-fixture.ts), whose neighbouring test rebuilds every transaction from `states[].data` and the test keys; this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys are the record fixture's three plus `44` repeated for the second owner and `55` for the third; test keys, published deliberately.

| Property | What it pins |
|---|---|
| `makerKey`, `serverKey`, `owner1Key`, `owner2Key`, `owner3Key`, `lockingKey` | The five test identities, and the lock of the first four states (the maker's). |
| `ownerProtocol`, `owner3OwnerKey`, `owner1OwnerKey`, `owner3OwnerLinkage` | The owner protocol `[1, 'dpp owner v1']`; the per-passport owner keys of owners 3 and 1, each their root derived under it with the passport identifier as key identifier and counterparty `self` (record-model §3); and owner 3's linkage scalar, with `owner3OwnerKey = owner3Key + scalar·G` (record-model-v2 §6). Reproducible from the test keys; only the root can produce the scalar, anyone can check it. |
| `states[]` | Six states in chain order: `ACTIVATE` by the maker, `SOLD` by the maker, `TRANSFER` to the second owner signed by the first, `REPAIRED` by the second owner, `TRANSFER` by the second owner to the third owner's derived key, and `TRANSFER` by the third owner to the first owner's derived key, whose `event_data` carries owner 3's scalar under `owner_linkage`, a property no reader interprets (record-model §3, field 9). Each carries `data` (the twelve posted fields), both signatures, `txid`, `outputIndex`, `lockingKey` (the maker's for the first four; for the last two the new owner's derived key, which is the state's own field 6: the possession convention), `unlock` (`owner` on the sixth state, whose input the third owner's wallet spent through the PushDrop unlock under the owner protocol with one derivation and no key export; `none` elsewhere, those inputs left unsigned because a verifier does not run scripts), the output's `lockingScript`, and the complete `rawTx`. The `SOLD` transaction carries its DPP output at index 1 behind an `OP_RETURN`, so outpoint tracking is tested rather than assumed. |
| `refusals[]` | Nine transactions, each extending a prefix of the valid chain (`appendAfter` names the last valid state kept; `-1` means the vector stands alone as a genesis) and breaking exactly one invariant of record-model §6, each naming the `error` a conforming verifier reports: a genesis that is not `ACTIVATE`, a genesis carrying `previous_txid`, two DPP outputs in one transaction, `ACTIVATE` after genesis, `previous_txid` naming a transaction other than the one spent, spending a different output of the right transaction, a changed `passport_id`, an owner change off `TRANSFER`, a payload change off `ACTIVATE`/`EDIT`/`TRANSFER`. The seven refusals of the owner-signed transfer left the fixture when that option was removed from the standard on 12 November 2026. |

A conforming verifier parses every `rawTx`, needs no source transactions hydrated (the spend is checked from the input's own outpoint), accepts the six-state chain with every user signature valid and every link satisfied, verifies every server signature against `serverKey` when configured with it, and reports each refusal vector's chain invalid for the pinned reason. A verifier that does run scripts finds the sixth state's input a valid spend of the fifth state's output.

## Current complete-representation anchor

[attestation-anchor-v1.json](attestation-anchor-v1.json) is a portable synthetic fixture shared by the generic overlay implementations and registry. It includes the new signed native claim, complete secured bytes, digest, nine framed metadata fields, service signature, derived key and ten-field script. It is independently reproduced by the writer and checked by both decoders. New native commitments include the signature; historical anchor-v3 fixtures retain their older digest contract.

The current fixture is reproduced from the public test keys by `attestationV1Fixture()`. `attestationV1Vectors()` generates the corresponding [stack vectors](vectors/dpp/attestation-anchor/v1.json), including signature tampering, shifted boundaries, an uncompressed key, malformed UTF-8 and invalid tails. Those six refusals are pinned in that file only, which is why this one format keeps both forms. The published-file tests exercise these refusals and check both JSON forms against their generators.

Two further vector files cover the contracts added for operators and portable evidence: [`vectors/dpp/publisher-policy/v1.json`](vectors/dpp/publisher-policy/v1.json), generated by `publisherPolicyVectors()`, carries a valid three-version policy chain with the signing preimage and digest of every version and the keys active at five instants, a countersigned federation rotation and eleven refusals by name; [`vectors/dpp/evidence-package/v1.json`](vectors/dpp/evidence-package/v1.json), generated by `evidencePackageVectors()`, carries a valid signed package (files base64-encoded) with its manifest preimage and seven refusals, each with the three separate verdicts (structure, inventory, signature).

## `battery-lifecycle-v1.json`

## `evidence-v1.json`

The verification-report fixture of [`../spec/verification.md`](../spec/verification.md) §7: twenty evidence cases and, for each, the report a conforming verifier produces under report version 2, so an API, an embedded view and a standalone tool are compared on the same bytes and the same words. The leading copy is [`../packages/dpp-protocol/test/evidence-v1-fixture.ts`](../packages/dpp-protocol/test/evidence-v1-fixture.ts); this JSON is regenerated verbatim from it and a test in that package holds the two identical. Every case is built from `chain-v1.json` and `attestation-anchor-v1.json` and their published test keys, plus a rival genesis and a re-signed anchor made from those keys, so every signature is reproducible and nothing needs a wallet or a network.

| Property | What it pins |
|---|---|
| `checkedAt` | The observation time injected into every report, so `checkedAt` and `observedAt` compare equal across implementations. |
| `cases[].evidence` | Token history as raw transaction hex, optional BUMP hex per state (`merklePaths`), alternative histories, native claims as posted and anchors as locking-script hex with optional exact secured bytes. |
| `cases[].expectedSubject` | The subject the verifier was asked about and where it came from (§3). |
| `cases[].policy` | The publisher keys, the managed-custody selection, control authorities and authority lists applied; `chainTracker` is `scripts-only` or `header-source`, and `headerSource` maps a height to the root the source holds or is `unavailable` for an outage. |
| `cases[].observers` | Declarative latest-state sources that answer as written: `unspent`, `spent` with the spending txid, `not-found`, `unavailable`. |
| `cases[].report` | The pinned report: sixteen checks in order, observations and limits. |

A conforming verifier rebuilds the evidence from the hex, answers the declared observers and header source as written, injects `checkedAt`, and produces a report equal to `report`, case by case. `node examples/verify-passport.mjs --fixture --report` is the standalone surface doing exactly that, one sentence per case. The cases cover a valid chain with and without proofs, a header outage, a refuted proof, a valid stale prefix that a source saw superseded, a missing middle, two DPP outputs in one transaction, a wrong publisher key, a signed substitution of one product for another, a subject the verifier did not expect independently, a duplicate genesis with and without a selecting expectation, genesis authority, the portable anchor with its claim with and without an authority policy, tampered secured bytes, mismatched anchor metadata, an unsupported representation, absent secured bytes and empty evidence.

## `vectors/dpp/exchange/`

The vectors of the exchange profiles that this repository issues under: `epcis-event-vc/v1.json`, the directly signed EPCIS event (`spec/epcis-event-profile.md`), eighteen credentials signed by two parties whose test scalars are published, with their findings and the anchor fields a registry derives. Generated by `packages/dpp-protocol/test/epcis-event-vectors.ts` and held equal to it by `epcis-event-vectors.test.ts`.
