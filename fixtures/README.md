# Conformance fixtures

**Status: the seed of the conformance suite, not the suite.** These files pin wire formats byte for byte, so that independent implementations that cannot import one another stay in agreement by testing against the same bytes. A fixture is not an elegant contract, but it is the kind that fails loudly: change a field order, a canonicalisation rule, a protocol string or a signing preimage anywhere, and a suite goes red with a diff you can read.

Two rules these files follow, and any future fixture must:

1. **Refusal vectors are part of the fixture.** A fixture with only positive vectors certifies that an implementation accepts what it should, and never that it refuses what it must. Every fixture that pins a signed layout carries variants a conforming reader is required to reject.
2. **Copies are verbatim.** Implementations vendor these files unchanged and assert against them in their own suites. Fixing a divergence means changing the implementation, never the fixture, unless the specification itself has changed, in which case the format's version identifier changes with it.

## Two forms, one set of bytes

The JSON files at the top of this directory are the bespoke form: one object per format, every pinned value a property, refusal variants beside them. `vectors/` holds the same bytes in the BSV stack's cross-language conformance vector format (`conformance/VECTOR-FORMAT.md` and `conformance/schema/vector.schema.json` in `bsv-blockchain/ts-stack`): a file with a stable dotted identifier, a version, the reference implementation that produced it and a parity class, holding vectors that each carry an identifier, an input, an expected result and tags. Positive vectors are tagged `happy-path`, refusals `error-case`, and binary is lower-case hex under keys ending `_hex`. Any runner that reads the stack's corpus reads these, and the stack's structural runner validates them as they stand: `node conformance/runner/src/runner.js --validate-only --vectors <this directory>/vectors` from a checkout of `ts-stack` with the runner's dependencies installed, exit code 0 clean, 2 malformed.

Both forms are generated by the packages' tests, as each section below names, and neither is edited by hand. The vector form is a pure mapping from the bespoke object: `packages/dpp-core/test/record-v1-vectors.ts` and `chain-v1-vectors.ts` for the version 1 record and chain, `record-v2-vectors.ts`, `chain-v2-vectors.ts` and `managed-acceptance-v1-vectors.ts` for the version 2 record, chain and acceptance record, `packages/overlay-topics/test/anchor-v3-vectors.ts` for the historical anchor and `packages/overlay-topics/test/attestation-v1-fixture.ts` for the current anchor, and a test in each package holds every published file identical to what its generator produces. To change a published file, change the module that generates it and run the suites with `REGENERATE_FIXTURES=1`, which rewrites the files before comparing them; the diff is the review. A difference between the two forms is a generation defect, fixed by regenerating. The vector files carry two things the bespoke files do not. The synthetic test private keys are published in the positive vectors (`11`, `22` and `33` repeated to 32 bytes for the record, `44` and `55` besides for the chain; `77` and `88` for the anchor), so a writer in any language reproduces the pinned bytes rather than only checking them; nothing derived from these keys will ever hold value. And the anchor vectors carry four refusals the bespoke file lacks: one over each of the three length bounds in [`../spec/legacy-uora-anchor-v3.md`](../spec/legacy-uora-anchor-v3.md) §5, and a claim whose `passportId` exceeds the bound §3 sets, each built by the generator from the pinned fixture rather than pinned again, one field extended past its bound and everything else untouched, so the bespoke file the implementing repositories hold verbatim is unchanged. Vector identifiers are permanent once published and files are append-only: a corrected expectation is a new vector, and the old one is marked skipped with a reason, which is the stack's rule and now this directory's.

A conformance report over these vectors is presented as [`../GOVERNANCE.md`](../GOVERNANCE.md) requires: one sentence per vector, refusals included, and no aggregate score. The runner's per-vector output is the data; the sentences are the presentation.

## `anchor-v3.json`

One complete `uora-anchor-v3` anchor, from the attestation claim through its canonical bytes, digest, derived locking key and full locking script, as [`../spec/legacy-uora-anchor-v3.md`](../spec/legacy-uora-anchor-v3.md) defines. The leading copy is [`../packages/overlay-topics/test/anchor-v3-fixture.ts`](../packages/overlay-topics/test/anchor-v3-fixture.ts); this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys involved are test keys, published deliberately; nothing derived from them will ever hold value.

| Property | What it pins |
|---|---|
| `attestation` | The claim exactly as posted, signed properties included. |
| `canonical` | The canonical bytes of that claim, as a string (spec §4). |
| `digest` | SHA-256 of the canonical bytes: the anchor's field 2. |
| `issuerDid`, `issuerKey` | The claiming party's two names for one key. |
| `anchoredBy` | The anchoring service's identity key: field 7. |
| `lockingKey` | The BRC-42 child the output must lock to, reproducible from `anchoredBy` and the attestation id. |
| `lockingScript` | The whole output, hex. Deterministic: signatures use RFC 6979 nonces, so this is reproducible on any machine from the test keys. |
| `boundaryShifted` | Four re-cut variants of the same output with the signature bytes untouched. Every one must be refused. They all verified under the superseded layout, which is why the current one exists. |
| `uncompressedKey` | The same output with its locking key re-pushed in the 65-byte uncompressed spelling. Attribution still matches after decoding, which is exactly why a lenient reader admitted it invisibly; a conforming reader refuses it at the push. |
| `malformedTail` | The same output with its drop tail wrong three ways: one drop short, the right total in the wrong opcodes, and a trailing chunk after a correct tail. A conforming reader validates the tail exactly and refuses each. |

A conforming writer reproduces `lockingScript` from `attestation` and the test keys. A conforming reader parses `lockingScript` to the fields above, verifies the field-8 signature over the SHA-256 of the length-delimited preimage, checks the locking key, and refuses every script in `boundaryShifted`, `uncompressedKey` and `malformedTail`.

## `record-v1.json`

One complete DPP record-model v1 output, from the posted state through its signing preimages, signatures, derived verification keys and full locking script, as [`../spec/record-model.md`](../spec/record-model.md) defines. The leading copy is [`../packages/dpp-core/test/record-v1-fixture.ts`](../packages/dpp-core/test/record-v1-fixture.ts), whose neighbouring tests rebuild every pinned byte from `state` and the test keys; this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys involved are test keys, published deliberately; nothing derived from them will ever hold value.

| Property | What it pins |
|---|---|
| `state` | The twelve data fields exactly as posted. |
| `ownerBlob` | The off-chain owner-tier blob whose SHA-256 is field 11 (spec §7). |
| `userPreimage`, `serverPreimage` | The two signing preimages: fields 1 to 12 concatenated raw, then the same followed by the user signature bytes (spec §5). |
| `userSignature`, `serverSignature` | DER ECDSA over SHA-256 of the preimages. Deterministic: RFC 6979 nonces, so both are reproducible on any machine from the test keys. |
| `userVerificationKey`, `serverVerificationKey` | The BRC-42 children the signatures verify under, re-derivable from on-chain data plus the published service identity (spec §5). |
| `lockingKey`, `lockingScript` | The whole output: key push, `OP_CHECKSIG`, fourteen minimal pushes, seven `OP_2DROP` (spec §2). |
| `uncompressedKey` | The same output with its locking key re-pushed in the 65-byte uncompressed spelling; a conforming reader refuses it at the push. |
| `malformedTail` | The drop tail wrong three ways: one drop short, the right drop total in the wrong opcodes, and a trailing chunk after a correct tail. A conforming reader validates the tail exactly and refuses each. |
| `rolledTimestamp` | Field 5 as `2026-02-30T00:00:00Z`, a date the calendar does not contain; hosts that roll it into March accepted it invisibly. Refused at decode. |
| `mangledUtf8` | `payload_public` as the bytes `22 ff 22`: invalid UTF-8 whose lossy decode is the valid JSON string `"�"`. Refused at the bytes, not after them. |
| `nulPassportId` | `passport_id` pushed non-minimally as the single byte `0x00`, which no field may be: minimal writing spells that value `OP_0`, and `OP_0` reads back as the empty field. Refused. |
| `emptyPushdata` | `event_data`'s `OP_0` re-encoded as a zero-length `PUSHDATA1`; `OP_0` is the only accepted encoding of the empty field. Refused. |
| `overlongPassportId` | `passport_id` at 513 bytes, one over the bound spec §3 sets because the field is a BRC-42 key identifier and a conforming wallet has a ceiling. Refused at decode, before any signature is checked. |

A conforming writer reproduces `lockingScript` from `state` and the test keys. A conforming reader parses `lockingScript` back to the state, verifies the user signature under `userVerificationKey`, and refuses every script in `uncompressedKey`, `malformedTail`, `rolledTimestamp`, `mangledUtf8`, `nulPassportId`, `emptyPushdata` and `overlongPassportId`.

## `chain-v1.json`

One complete DPP record-model v1 passport chain, six states long, and the broken links a verifier must refuse, as [`../spec/record-model.md`](../spec/record-model.md) §6 and [`../spec/custody.md`](../spec/custody.md) §3 and §4 define. `record-v1.json` pins one output; this pins what holds outputs together, and how an owner's own wallet holds and hands over a passport. The leading copy is [`../packages/dpp-core/test/chain-v1-fixture.ts`](../packages/dpp-core/test/chain-v1-fixture.ts), whose neighbouring test rebuilds every transaction from `states[].data` and the test keys; this JSON is regenerated verbatim from it, and a test in that package holds the two identical. The keys are the record fixture's three plus `44` repeated for the second owner and `55` for the third; test keys, published deliberately.

| Property | What it pins |
|---|---|
| `makerKey`, `serverKey`, `owner1Key`, `owner2Key`, `owner3Key`, `lockingKey` | The five test identities, and the lock of the first four states (the maker's). |
| `ownerProtocol`, `owner3OwnerKey`, `owner1OwnerKey`, `owner3OwnerLinkage` | The owner protocol `[1, 'dpp owner v1']`; the per-passport owner keys of owners 3 and 1, each their root derived under it with the passport identifier as key identifier and counterparty `self` (record-model §3); and owner 3's linkage scalar, with `owner3OwnerKey = owner3Key + scalar·G` (custody §4). Reproducible from the test keys; only the root can produce the scalar, anyone can check it. |
| `states[]` | Six states in chain order: `ACTIVATE` by the maker, `SOLD` by the maker, `TRANSFER` to the second owner signed by the first, `REPAIRED` by the second owner, `TRANSFER` by the second owner to the third owner's derived key (the equality form of consent: field 7 equals the previous field 6), and `TRANSFER` by the third owner to the first owner's derived key carrying `owner_linkage` in `event_data` (the linkage form). Each carries `data` (the twelve posted fields), both signatures, `txid`, `outputIndex`, `lockingKey` (the maker's for the first four; for the last two the new owner's derived key, which is the state's own field 6: the possession convention), `unlock` (`owner` on the sixth state, whose input the third owner's wallet spent through the PushDrop unlock under the owner protocol with one derivation and no key export; `none` elsewhere, those inputs left unsigned because a verifier does not run scripts), the output's `lockingScript`, and the complete `rawTx`. The `SOLD` transaction carries its DPP output at index 1 behind an `OP_RETURN`, so outpoint tracking is tested rather than assumed. |
| `refusals[]` | Sixteen transactions, each extending a prefix of the valid chain (`appendAfter` names the last valid state kept; `-1` means the vector stands alone as a genesis) and breaking exactly one rule, each naming the `error` a conforming verifier reports. Nine break an invariant of record-model §6: a genesis that is not `ACTIVATE`, a genesis carrying `previous_txid`, two DPP outputs in one transaction, `ACTIVATE` after genesis, `previous_txid` naming a transaction other than the one spent, spending a different output of the right transaction, a changed `passport_id`, an owner change off `TRANSFER`, a payload change off `ACTIVATE`/`EDIT`/`TRANSFER`. Seven carry `ownerConsent: true` and break the owner-signed transfer of custody §4, in each of its ways: a transfer by a stranger, by the former owner, with the wrong scalar, with an upper-case scalar, with a 63-character scalar, with the scalar inside a JSON array, and a recovery by the maker with no authority named. Every one of the seven is a valid chain when the option is off, which a conforming verifier also demonstrates, and `recoveryWithoutAuthority` carries `acceptedUnder`, the transfer authorities under which the same bytes are accepted. |

A conforming verifier parses every `rawTx`, needs no source transactions hydrated (the spend is checked from the input's own outpoint), accepts the six-state chain with every user signature valid and every link satisfied, verifies every server signature against `serverKey` when configured with it, reports the owner-signed transfer as holding on the three `TRANSFER` states and as not applicable on the rest when configured with the option, and reports each refusal vector's chain invalid for the pinned reason under the option the vector names. A verifier that does run scripts finds the sixth state's input a valid spend of the fifth state's output.

## Current complete-representation anchor

[attestation-anchor-v1.json](attestation-anchor-v1.json) is a portable synthetic fixture shared by the generic overlay implementations and registry. It includes the new signed native claim, complete secured bytes, digest, nine framed metadata fields, service signature, derived key and ten-field script. It is independently reproduced by the writer and checked by both decoders. New native commitments include the signature; historical anchor-v3 fixtures retain their older digest contract.

The current fixture is reproduced from the public test keys by `attestationV1Fixture()`. `attestationV1Vectors()` generates the corresponding [stack vectors](vectors/dpp/attestation-anchor/v1.json), including signature tampering, shifted boundaries, an uncompressed key, malformed UTF-8 and invalid tails. The published-file tests exercise these refusals and check both JSON forms against their generators.

Two further vector files cover the contracts added for operators and portable evidence: [`vectors/dpp/publisher-policy/v1.json`](vectors/dpp/publisher-policy/v1.json), generated by `publisherPolicyVectors()`, carries a valid three-version policy chain with the signing preimage and digest of every version and the keys active at five instants, a countersigned federation rotation and eleven refusals by name; [`vectors/dpp/evidence-package/v1.json`](vectors/dpp/evidence-package/v1.json), generated by `evidencePackageVectors()`, carries a valid signed package (files base64-encoded) with its manifest preimage and seven refusals, each with the three separate verdicts (structure, inventory, signature). The Python reader under `conformance/independent/` reproduces both.

## `battery-lifecycle-v1.json`

The marked industrial-battery demonstration lifecycle (`spec/profiles.md`, `spec/rules.md` §2): a synthetic passport under the GS1 demonstration prefix 952 (`https://dpp.bsvb.net/01/09521000000018/21/BATT-0001`, check digit computed) carried through ACTIVATE, SOLD with dispatch and receipt evidence, a TRANSFER of token control with no custody evidence, REPAIRED by a service party, an EDIT that records a measured value, and RECYCLED into outputs with new identities. Each state carries its raw transaction, its signed native lifecycle claim, the evidence facets put forward and the conditional mapping result, and the file ends with the one verification report over the chain and the claims. The TRANSFER maps to `insufficient-data` with `custodyRecord` missing: a token transfer never implies delivery. No product exists; every value is invented and the payload says so. Generated by `packages/dpp-profiles/test/battery-lifecycle.test.ts`.

Identifiers in the fixtures: the pinned `record-v1` and `chain-v1` fixtures, and everything derived from them (`evidence-v1`, the record and chain vectors), carry GS1's published example number `09506000134352` under `id.gs1.org`, because their bytes were frozen before the identifier decision and a pinned fixture's bytes change only with the format's version identifier. The battery lifecycle fixture and every new fixture carry a number under the GS1 demonstration prefix 952 at `dpp.bsvb.net` (`09521000000018`, check digit computed). Moving the version-1 fixtures to a 952 number is a version-2 fixture set, a maintainers' decision recorded in `docs/identifiers.md`.

## `evidence-v1.json`

The verification-report fixture of [`../spec/verification.md`](../spec/verification.md) §7: twenty-one evidence cases and, for each, the report a conforming verifier produces, so an API, an embedded view and a standalone tool are compared on the same bytes and the same words. The leading copy is [`../packages/dpp-core/test/evidence-v1-fixture.ts`](../packages/dpp-core/test/evidence-v1-fixture.ts); this JSON is regenerated verbatim from it and a test in that package holds the two identical. Every case is built from `chain-v1.json` and `attestation-anchor-v1.json` and their published test keys, plus a rival genesis and a re-signed anchor made from those keys, so every signature is reproducible and nothing needs a wallet or a network.

| Property | What it pins |
|---|---|
| `checkedAt` | The observation time injected into every report, so `checkedAt` and `observedAt` compare equal across implementations. |
| `cases[].evidence` | Token history as raw transaction hex, optional BUMP hex per state (`merklePaths`), alternative histories, native claims as posted and anchors as locking-script hex with optional exact secured bytes. |
| `cases[].expectedSubject` | The subject the verifier was asked about and where it came from (§3). |
| `cases[].policy` | The publisher keys, owner-consent selection and authority lists applied; `chainTracker` is `scripts-only` or `header-source`, and `headerSource` maps a height to the root the source holds or is `unavailable` for an outage. |
| `cases[].observers` | Declarative latest-state sources that answer as written: `unspent`, `spent` with the spending txid, `not-found`, `unavailable`. |
| `cases[].report` | The pinned report: sixteen checks in order, observations and limits. |

A conforming verifier rebuilds the evidence from the hex, answers the declared observers and header source as written, injects `checkedAt`, and produces a report equal to `report`, case by case. `node examples/verify-passport.mjs --fixture --report` is the standalone surface doing exactly that, one sentence per case. The cases cover a valid chain with and without proofs, a header outage, a refuted proof, a valid stale prefix that a source saw superseded, a missing middle, two DPP outputs in one transaction, a wrong publisher key, an unproven owner consent, a signed substitution of one product for another, a subject the verifier did not expect independently, a duplicate genesis with and without a selecting expectation, genesis authority, the portable anchor with its claim with and without an authority policy, tampered secured bytes, mismatched anchor metadata, an unsupported representation, absent secured bytes and empty evidence.
